# Нейро-СММ Ассистент — правила для security-guidance

Проектные правила поверх встроенных проверок плагина (инъекции/XSS/SSRF/секреты и т.п. уже покрыты built-in — здесь только специфика этого кодбейза).

- **Секреты только через `.env`, никогда в код/коммит.** `OPENROUTER_API_KEY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_ADMIN_CHAT_ID`, `VK_SERVICE_TOKEN`, `SMTP_HOST`/`SMTP_PORT`/`SMTP_USER`/`SMTP_PASS`/`SMTP_FROM`. Не логировать их значения целиком (в т.ч. частично замаскированными, если маска предсказуема).

- **Magic-ссылки и session-токены (`access_links`, cookie сессии) — это bearer-креды, не просто идентификаторы.** Не логировать токен целиком (только последние символы, если вообще нужно), не подставлять напрямую в текст ответа за пределами предусмотренного потока (email/Telegram-уведомление). Ссылка одноразовая и не привязана к IP по дизайну — не "чинить" это привязкой к IP без обсуждения (осознанное архитектурное решение, раздел 2 спецификации).

- **Порядок роутеров с `router.use(requireSession)` в `backend/src/index.ts` — источник реальных auth-багов, а не гипотетический.** Любой роутер, вызывающий `requireSession` без пути, перехватывает вообще любой дошедший до него запрос и сам отвечает 401, не вызывая `next()`. Публичные роуты (`resultsRouter`, `accessRouter` и любые будущие публичные ручки) обязаны быть смонтированы раньше защищённых (`onboardingRouter`, `agentsRouter`, `reelsReferencesRouter`) — иначе публичный путь никогда не будет достигнут. При добавлении нового роутера — явно проверять его место в `app.use(...)` относительно существующих `requireSession`-роутеров.

- **Проверка владения ресурсом по `clientId` из сессии, не по одному `id` из URL/body.** Пример уже реализован верно — `DELETE /api/reels-references/:id` сверяет `clientId` из сессии перед удалением. Любой новый эндпоинт с `:id` в пути (удаление/чтение чужого ресурса по id) обязан делать ту же проверку — не доверять, что клиент не подставит чужой id (IDOR).

- **Загрузка файлов (`multer`, `/uploads/<client_id>/<category>/`, `/uploads/reels/...`) — категория/путь всегда берутся из параметра маршрута или захардкоженного enum, не из пользовательского текста.** Не строить путь на диске конкатенацией произвольной строки от клиента без валидации против path traversal (`..`, абсолютные пути). Имя файла (`originalname`) используется только для отображения/скачивания — не для построения пути на диске.

- **`/media` и `/uploads` — публичные статические маунты без авторизации (осознанное решение, раздел 7 спецификации).** Ничего чувствительного (чужие клиентские данные, не предназначенные для конкретного URL-получателя) туда не должно попадать. Не добавлять в эти каталоги файлы, для которых нужен контроль доступа — для этого нужен отдельный защищённый путь, не `express.static`.

- **CLI-админка (`admin:list`/`admin:approve`/`admin:reject`) намеренно не имеет HTTP-эквивалента.** Не добавлять HTTP-роут для подтверждения/отклонения заявок или другого админ-действия без явного решения пользователя — self-hosted сервер с одним оператором, лишняя HTTP-поверхность здесь не нужна и не защищена отдельной аутентификацией.

- **Контент, спарсенный с чужих соцсетей (`fetchPosts`, посты конкурентов/клиента через `telegram.ts`/`vk.ts`), — недоверенный внешний текст, который дальше идёт в промпт LLM-агентам.** Это не строится в SQL/shell-команды напрямую, но при добавлении новой логики, которая исполняет что-то на основе этого текста (не просто передаёт его моделью как контекст) — относиться как к недоверенному вводу.

- **SQLite/Drizzle — только параметризованные запросы через ORM.** Не собирать SQL конкатенацией строк с пользовательским вводом (email, ссылки, ответы анкеты и т.п.) — все текущие запросы через Drizzle это уже соблюдают, сохранять паттерн в новом коде.
