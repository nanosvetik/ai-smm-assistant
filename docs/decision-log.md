# Журнал решений

Почему сделано так, а не иначе. Читать, когда возникает соблазн переиграть уже принятое решение или когда непонятна причина странного на вид кода. Текущее состояние — `docs/backend-state.md` / `docs/frontend-state.md`, грабли — `docs/gotchas.md`, архитектура — `docs/project-specification.md`.

## Модели агентов

### `audience-unpacker` / `expertise-unpacker`: Sonnet → DeepSeek Pro → обратно Sonnet

Три точки данных, из них две отрицательные:

1. **Контролируемый тест на `expertise.md`** показал реальные провалы DeepSeek V4 Pro на сложных мета-шагах промпта против Claude Sonnet 5.
2. **2026-09-01 — решение пересмотрено в пользу дешёвой модели:** если в демо-режиме глубины анализа всё равно не будет (из-за короткой анкеты, а не из-за модели), платить за Sonnet незачем. Провизорно, с условием отката при живом провале.
3. **2026-09-03 — провал произошёл.** `expertise_profiles` версии 1 клиента `landing-hero-yoga-client` содержала не документ, а буквально `<tool_calls><tool_call name="web_fetch">{"url": "https://t.me/derzhimplanku",...}</tool_call></tool_calls>` — модель галлюцинировала вызов несуществующего инструмента вместо текста (бэкенд не передаёт в OpenRouter вообще никаких `tools`). Это хуже, чем «поверхностный анализ»: полный отказ выдать документ. `parseFrontmatter` честно ничего не нашёл, код подставил дефолтный `черновик-рамка`, фронтенд отрендерил обрывок как обычный текст.
4. **2026-09-05 — откат на Claude Sonnet 5.** Не потому что первый полный живой прогон вышел плохим (наоборот: оба документа содержательные, с нетривиальными инсайтами из скудной анкеты), а потому что один чистый прогон не отменяет вывод о нестабильности. Дополнительно: `audience-unpacker` — первый агент, которого вообще видит клиент после анкеты, а УТП продукта «честно, не нейрослоп»; сбой тут бьёт по УТП сильнее, чем в середине пайплайна. Стоимость переключения ограничена — два вызова на клиента, не масштабируется по постам/дням.

Изменена только константа `MODEL` в `audienceUnpacker.ts`/`expertiseUnpacker.ts`, промпты не тронуты.

### `content-planner` / `copywriter`: Flash → Pro (2026-09-02)

Повод — разбор реального вывода, где сразу нашлись примеры бессвязного текста: «Утром помято как подушка?» (несвязный образ), «Канализация для лица» (натянутая метафора), «за час снял отёк… за 5 минут» (противоречие внутри текста). Оба агента синтезируют поверх готовых документов, поэтому изначально казались задачей для Flash — но связность самого генерируемого текста (не структуры документа) оказалась недостаточной. Изменена только константа `MODEL`. Сравнительного теста Pro vs Flash не проводилось — решение принято по одному явному примеру.

### `reels-writer`: Pro, хотя спецификация говорит «DeepSeek V4»

Раскадровка и хук на 3 секунды требуют более сильной творческой части, чем обычный пост. В таблице раздела 4 спецификации строка без суффикса — на OpenRouter реально существуют только `-flash`/`-pro`.

### `visual-style-analyzer`: Claude Sonnet 5, не дешёвая vision-модель

`deepseek/deepseek-v4-flash-vision-exp` потребовала бы включить в OpenRouter разрешение на обучение на входных данных. Вход здесь — drag-and-drop референсы клиента (кабинет, «до/после»), не публичные посты. Не включили.

## Продукт и UX

### Единственный канал связи — email (2026-09-03)

Пересматривает более раннее решение про выбор канала email/telegram/vk. Причина: почта есть у всех, и на неё же можно будет написать с предложениями позже. Плюс Telegram и ВК всё равно не могут написать клиенту первыми, так что реального выбора для доставки не было. Вопрос очерёдности Telegram/ВК (deep-link для `chat_id`, VK Callback API) снят с повестки, не отложен.

### Кнопка «Переделать» убрана полностью (2026-09-02)

Расширяет более узкое отложенное решение «убрать только с пяти честных этапов перед деплоем». Причина сместилась с честности на прямой контроль над платными вызовами: «это демо, нечего играться за мой счёт» — Claude Sonnet 5/DeepSeek не бесплатны даже для текстовых этапов. `RunBlock` рендерит кнопку только пока `!result`.

Медиа разошлись по цене: **картинки** ($0.04) — «Сгенерировать заново» остаётся (снимок с рулём, показанный в тот же день, — живое доказательство, что генерация может выйти с браком: обрубленная человеческая фигура, впритык к предмету переднего плана; без регенерации демо-клиент получил бы это как финал). **Видео** ($0.84) — регенерации нет, первая генерация окончательная.

### Референсы — только для рилсов, после сценария (2026-09-02)

Раньше единственный вход референсов был drag-and-drop на онбординге (5 категорий), общий для `visual-style-analyzer`. Клиент грузил фото до того, как знал тему рилса, и `reels-writer` угадывал релевантность по названию категории. Референсы изначально задумывались только для рилсов, и правильнее добавлять их под готовый сценарий.

Новая таблица `reels_reference_files` **сознательно отдельная** от `reference_files` — `visual-style-analyzer` агрегирует референсы по `clientId` без фильтра по категории, общая таблица была бы прямой утечкой в обход решения. Старый эндпоинт и таблица в коде не тронуты, но фронтенд в них больше не пишет.

### Визуальный стиль картинок синтезирует `account-packager` из текста (2026-09-02)

Полная замена прежнего источника (`ensureVisualStyleProfile` по фото клиента) для картинок-постов. `account-packager` получил Шаг 4 «Визуальный стиль» (палитра/свет/композиция/чего избегать — из позиционирования, ЦА и метода, с заземлением по «Аудиту шапки профиля», если он есть), и рекомендация **передаётся дальше** в `visual-generator` — стиль единый для всех будущих иллюстраций, не только для демо-позиций MVP.

`visual-style-analyzer` **не удалён** намеренно — просто для картинок не вызывается, остался только у `reels-video-generator`.

Живой тест подтвердил передачу данных прямым текстовым соответствием, не совпадением: `account-packager` выдал «тёплая приглушённая палитра, мягкий рассеянный свет, просторная минималистичная композиция», `visual-generator` — `dusty green`, `beige`, `soft diffused light`, `spacious minimal composition`.

### Панель экспорта сужена до «Копировать»/«Скачать» (2026-09-03)

Редактируемое текстовое поле из раздела 6 спецификации не делаем вообще — клиент копирует текст и правит его сам, вне инструмента. Реализовано только для постов (`copywriter`), сценарий рилса и results-страница не тронуты.

### Доступ после истечения 24-часовой сессии (2026-09-06)

Обсуждение началось с вопроса, вернётся ли клиент только на страницу результатов — выяснилось, что повторного входа в кабинет вообще не существует (`SESSION_TTL_MS` = 24ч, онбординг-ссылка сгорает при первом переходе). Решили **не строить инфраструктуру повторного входа**, а расширить то, что и так переживает сессию (results-ссылка, 90 дней):

- В results добавлена «Упаковка профиля» — безопасна для показа третьим лицам, сама демонстрирует ценность продукта при пересылке (лид-магнит).
- Контент-план остался только в кабинете, но с явным предупреждением скачать его — единственный документ без другого способа сохраниться.
- Сырые аналитические документы (ЦА, экспертность, анализ аккаунта/конкурентов, аудит шапки) **сознательно сгорают** вместе с сессией: это стимул вернуться за полной версией, часть логики демо, не недоработка. Контент-план в results не кладём — это личная стратегия клиента на 2 недели, не материал для случайных зрителей пересланной ссылки.

### Тексты писем со ссылками (2026-09-05)

Раньше оба письма подставляли `expiresAt.toISOString` и упоминали одноразовость одной сухой фразой. Новый текст онбординг-письма прямо предупреждает: если открыть ссылку из любопытства, не будучи готовым проходить анкету, она сгорит и восстановить её нельзя — переходить только когда готовы заполнить всё за 10–15 минут. Results-письмо дополнено сроком и явным приглашением пересылать друзьям/коллегам (это и есть заложенная механика лид-магнита). Первая формулировка содержала «ссылка ваша навсегда в пределах 90 дней» — противоречие поймано при вычитке, «навсегда» убрано.

### `run-all` не подключён к UI и не будет

Опасение было, что 8-минутный прогон не переживёт HTTP-таймаут браузера/прокси и `run-all` придётся переделывать в фоновую задачу с поллингом/SSE. На практике кабинет получил кнопку «Запустить» на каждом этапе отдельно — продуктового пути к `run-all` просто нет. Эндпоинт и `pipeline.ts` оставлены для сквозных live-тестов при разработке; переделывать незачем, пока не появится реальный сценарий.

### Рамка ожиданий для тех, кто «пришёл потыкать MVP»

Честный `черновик-рамка` с кучей `требует уточнения у эксперта` — корректное поведение при 5 коротких полях вместо 30–60-минутного интервью, но без контекста читается как «сломано». Решили не размазывать пояснение по кабинету (Бриф 2 просит там скорость и ясность, не убеждение), а сказать один раз на экране «Данные сохранены» и коротко напомнить в момент растерянности — рядом со `StatusLine` при статусе `черновик-*`.

## Инфраструктура

### Размещение и выход в интернет (2026-09-09)

Сервис размещается на **российском хостинге**: клиенты из России, зарубежный хост рискует попасть под блокировку. Выход к тем сервисам, которые с российского адреса недоступны, идёт через **собственный сервер за границей**, где уже стоит шлюз OmniRoute. Адреса машин и их состояние — `docs/infrastructure.local.md` (локальный, репозиторий публичный).

Что куда ходит:

| Через зарубежный сервер | Напрямую с российского |
|---|---|
| вызовы моделей: текст, картинки, видео | ВК: посты и шапка сообщества |
| парсер Telegram-каналов (`t.me/s/`) | сайт, файлы, база |
| бот-уведомления оператору | |

ВК через зарубежный сервер **не гнать**: из иностранных дата-центров у него больше ограничений, чем с российского адреса, и это лишний узел в цепочке, который может лечь.

**Выбран форвард-прокси с выборочным проксированием в коде** (принятое решение 2026-09-09, реализовано в тот же день). Исходная идея — гонять всё через OmniRoute — покрывала только текстовые вызовы: у шлюза OpenAI-совместимый API, медиа-эндпоинты OpenRouter в него не входят, а на видео схема ломается принципиально (`docs/gotchas.md`, «Внешние API»); Telegram через шлюз не проходит вообще.

Как сделано: на зарубежном сервере поднят `tinyproxy`, доступ к нему ограничен адресом боевого сервера и паролем. В коде — `lib/outboundProxy.ts` с `proxiedFetch` поверх `undici.ProxyAgent`; через прокси идут `lib/openrouter.ts`, `lib/imageGeneration.ts`, `lib/videoGeneration.ts`, `lib/telegram.ts`, `parsers/telegram.ts`, напрямую — `parsers/vk.ts` и `lib/email.ts`. Адрес прокси задаётся переменной `OUTBOUND_PROXY_URL`; пустая переменная = прямой выход, поэтому дев-машина работает без изменений.

Альтернативу (WireGuard-туннель с маршрутизацией на уровне системы) отклонили: маршруты задаются по IP-адресам, а у OpenRouter и Telegram они меняются — поддерживать и отлаживать дороже, чем явное проксирование в пяти файлах.

Проверено живьём с боевого сервера: через прокси `openrouter.ai` отдаёт `200` (было `403`), `api.telegram.org` и `t.me` отвечают (были таймауты); напрямую `api.vk.com` и `goapi.unisender.ru` работают.

Побочно: незакрытый вопрос проекта про SMTP может закрыться сам — блокировка исходящих 587/465 была свойством домашней сети, с хостинга отправка, скорее всего, заработает (см. «SMTP-провайдер» ниже).

### Бренд и домен (2026-09-04, уточнено 2026-09-05)

Название — **«Своими словами»** (стояло как рабочий вариант в `LandingScreen.tsx`, подтверждено без изменений). Домен — **`svoislova-ai.ru`**: первоначальный вариант, не связанный с названием, заменён на транслитерацию бренда с суффиксом `-ai`. Подвал «Собрано в «Ателье»» на results-странице был придуман по имени файла дизайн-брифа, не был подтверждённым названием — убран.

### SMTP-провайдер (2026-09-04)

Выбран личный Gmail оператора через App Password (новый Google-аккаунт не завёлся). `.env`: `SMTP_HOST=smtp.gmail.com`, `SMTP_PORT=587`, `SMTP_USER`/`SMTP_PASS`/`SMTP_FROM`.

**Живой тест отправки не пройден и не может быть пройден из сети разработки.** Прямые попытки подключения дают `ETIMEDOUT`/`ENETUNREACH` на портах 587 и 465, одинаково для `smtp.gmail.com` и контрольного `smtp.yandex.ru` — то есть блокировка исходящих SMTP-портов на уровне сети (провайдер/роутер), обычная практика против спам-ботов, не проблема логина или провайдера. Решение: конфиг оставляем, живую проверку откладываем до реального сервера; **не** переключаться на HTTP API-провайдера (Brevo и т.п.) заранее.

**Если на проде повторится тот же паттерн ошибок** — значит и хостинг блокирует исходящий SMTP (нередкий дефолт у облачных провайдеров), тогда возвращаться к HTTP API-провайдеру.

### Почта через HTTP API Unisender Go (2026-09-09)

Замена SMTP после того, как условие ниже наступило. Выбран **Unisender Go**: транзакционный сервис (не рассылочный), HTTP API на 443, серверы в РФ — существенно, потому что туда уходят адреса живых клиентов. Проверено, что с боевого сервера домены всех рассмотренных российских сервисов отвечают.

`lib/email.ts` переписан на `fetch` к `goapi.unisender.ru`; экспортируемый интерфейс (`isEmailConfigured`, `sendMail`) не изменился, вызывающий код (`admin/approval.ts`, `agents/resultsDelivery.ts`) не трогался. `nodemailer` из зависимостей убран. `.env`: `UNISENDER_API_KEY`, `MAIL_FROM`, необязательный `MAIL_FROM_NAME`.

Две особенности API, заложенные в код: он **отвечает HTTP 200 и на часть ошибок** (признак — поле `status` в теле), и успешный ответ может содержать `failed_emails` с отвергнутым адресом. Без обеих проверок отправка молча считалась бы удавшейся.

**Ответы клиента уводятся на живой ящик оператора** (`MAIL_REPLY_TO` → поле `reply_to`). У домена сервиса нет MX-записей, то есть на адрес отправителя физически некуда написать, а тексты писем и экранов предлагают ответить. Альтернатива — заводить почтовый хостинг на домене — для MVP избыточна.

**Первое письмо ушло в «Спам» у Gmail (2026-09-09).** Ожидаемо для домена, с которого никогда раньше не писали: SPF, DKIM и DMARC настроены, репутации ещё нет. Лечится временем и тем, что получатели помечают письма как «не спам». На лендинге в сообщение после отправки заявки добавлена просьба заглянуть в «Спам» с объяснением причины.

**Отслеживание переходов по ссылкам отключить нельзя без обращения в их поддержку** (`track_links: 0` требует разрешения на аккаунт). Это упиралось в отдельный вопрос про одноразовые magic-ссылки — см. «Одноразовые ссылки и почтовые роботы».

**Опасение не подтвердилось на живом письме (2026-09-09).** В пришедшем письме ссылка в теле осталась нетронутой (`https://svoislova-ai.ru/onboarding?token=...`), через трекинговый домен идёт **только ссылка отписки**. Похоже, подмена применяется к HTML-части, а письма сервиса — чистый текст (`body: { plaintext }`). Значит magic-ссылку трекер не переписывает и «прокликать» её своим редиректом не может. Проверять заново, если письма когда-нибудь станут HTML.

**Зато появился блок «Отписаться»** — следствие убранного `skip_unsubscribe` (см. выше). Для транзакционных писем это реальный риск, а не косметика: отписавшийся адрес попадает в чёрный список сервиса, и **второе письмо, со ссылкой на результаты, до клиента не дойдёт**. Код это увидит (`failed_emails` проверяется и бросает ошибку), но клиент останется без результата, а оператор узнает об этом только из логов. Правильное решение — запросить у поддержки Unisender флаг `allow_skip_unsubscribe` и вернуть поле в `lib/email.ts`. До этого блок отписки в письмах остаётся.

**Повторилось (проверено на боевом сервере 2026-09-09).** Ни один SMTP-порт с него не открывается: 587, 465 и 25, одинаково для Gmail, Яндекса и Mail.ru. То есть дело не в Gmail и не в географии — хостинг режет исходящий SMTP целиком, как антиспам-политику. Условие, записанное выше, наступило: **SMTP как транспорт с этого сервера нежизнеспособен.** Варианты — запрос в поддержку хостинга на снятие ограничения (иногда снимают) либо почтовый провайдер с HTTP API; выбирать российского, иначе упрёмся в ту же географию, что и с моделями. Решение не принято.

Побочная находка: DNS для `smtp.gmail.com`/`smtp.yandex.ru` в этой сети иногда возвращает только IPv6-адрес без реального маршрута (`ENETUNREACH`). Встроенный dual-stack резолвер nodemailer (`resolve4`+`resolve6`, IPv4 первым при успехе обоих) не спасает, если `resolve4` сам не отвечает; `lib/email.ts` этот случай не обрабатывает. Обходной путь, если увидим `ENETUNREACH` на сервере: резолвить через `dns.resolve4` вручную и подключаться по IP с `tls.servername` для SNI (паттерн проверен тестовым скриптом, скрипт в репозиторий не сохранён).

### Ссылка на анкету сгорает при отправке формы, а не при открытии (2026-09-09)

Было: первый же `GET /api/access/:token` помечал ссылку использованной. Проблема в том, что почтовые антивирусы и предпросмотр ссылок в почтовых клиентах ходят по ссылкам из письма **сами**, до человека — такой заход сжигал ссылку, и живой клиент получал «уже использована», не сделав ничего. Риск существовал и на SMTP; переход на Unisender Go его обострил, потому что там ссылки подменяются на трекинговые, а отключается это только через их поддержку (`track_links: 0` требует разрешения на аккаунт).

Лечение сознательно сделано на своей стороне, а не у провайдера: `usedAt` проставляется в `POST /api/onboarding` после успешного сохранения анкеты, а обмен ссылки на сессию её больше не трогает. Помечаются все живые onboarding-ссылки клиента: сессия не хранит токен, которым была получена, а больше одной такой ссылки бывает только если оператор выдал повторную.

Ограничение по времени (48 часов) работает как раньше и не зависит от этого. Пересдать форму клиент по-прежнему может: сессия живёт 24 часа, ссылка для этого не нужна.

Проверено живым прогоном: два открытия подряд дают сессию, отправка анкеты проходит, третье открытие возвращает `410 link_already_used`.

Формулировку MVP-объёма «одноразовая magic-ссылка» это уточняет, а не отменяет: ссылка по-прежнему на один онбординг.

### Docker — только для локального запуска, прод нативный (2026-09-09)

Compose поднимает связку «API + nginx со статикой» одной командой: репозиторий публичный, и человек, который его открыл, должен иметь возможность запустить проект, не разбираясь в устройстве монорепозитория.

На боевом сервере контейнеров нет намеренно. Там одна машина, SQLite файлом и файлы клиентов на диске — контейнеры добавили бы тома, права на них и лишний слой при отладке, не решив ни одной существующей задачи. Машина к тому же с 2 ГБ памяти, где сборка образов ощутима.

Раздача статики в compose повторяет прод-топологию: фронтенд и API за одним адресом, поэтому куке сессии не нужен CORS, а SPA-маршруты вроде `/onboarding/<токен>` отдаются как `index.html`. Проверка живости `/health` пробрасывается отдельным правилом — иначе она попадала бы в тот же SPA-фолбэк и отвечала «здоров» страницей интерфейса даже при мёртвом API.

### Веб-сервер на проде — Caddy, а не nginx (2026-09-10)

Локально в compose остаётся nginx, на боевом сервере поставлен Caddy. Причина одна и весомая: сертификат. Caddy выпускает и продлевает его сам, без отдельного acme-клиента, задания в cron и правил перезагрузки после обновления — то есть исчезает целый класс отказов «сертификат протух, потому что молча перестало отрабатывать продление». Конфигурация при этом короче nginx-овой: перенаправление с http и с www, подстановка `index.html` под маршруты интерфейса и проксирование `/api`, `/health`, `/media`, `/uploads` к приложению на локальном порту.

Расхождение с локальным nginx осознанное: nginx в compose нужен, чтобы проект поднимался одной командой без сертификатов и доменов, а там, где TLS не нужен, преимущество Caddy пропадает. Оба конфига описывают одни и те же правила; боевой лежит в `deploy/Caddyfile` под контролем версий, а не только на машине.

HSTS намеренно не включён на первый день. Заголовок заставляет браузеры ходить только по https в течение заявленного срока, и на новом домене с непроверенным продлением это необратимая ставка: при поломке сертификата запасного пути к сервису не останется. Включать после того, как продление отработает вживую хотя бы раз.

### SQLite, а не Postgres

Self-hosted одиночный сервер, не нужен отдельный процесс/контейнер БД, MVP-объём данных небольшой. Пересматривать, только если проект вырастет за пределы одного сервера или появится нужда в конкурентной записи.

### Данные клиента в SQLite, а не в `@modelcontextprotocol/server-memory`

Скорректировано после живого теста (2026-08-29): сервер по умолчанию пишет в один общий файл на весь компьютер (нашли в графе чужую сущность из несвязанного проекта), и даже со scoping через `MEMORY_FILE_PATH` это один stdio-процесс с одним файлом без блокировок при параллельной записи — не годится как хранилище для веб-бэкенда с множеством одновременных клиентов.

### Локальный диск, а не S3/R2

Раздача статики через nginx/Caddy. Тот же принцип self-hosted без лишних расходов, что и с БД.

### Telegram long polling, а не webhook

Не требует публичного HTTPS-домена.

### Админка — CLI, а не HTTP

Намеренно, чтобы не открывать лишнюю поверхность в сеть для self-hosted сервера с одним оператором.

### Промпты и код-оркестрация раздельно

`prompts/*.md` и `backend/src/agents/*.ts` — не колокация в одну папку на агента. Промпты изначально самостоятельные документы: эксперт может подгрузить их в любую другую нейросеть напрямую, это не только деталь реализации бэкенда.

### `smm-mcp` не в npm workspaces

Отдельный самостоятельный MCP-сервер со своим `npm install`. И он же — причина, по которой `lib/imageGeneration.ts`/`lib/videoGeneration.ts` реализуют вызовы напрямую: `smm-mcp` это stdio-сервер из `.mcp.json`, инструмент разработки, не HTTP-сервис, который мог бы вызвать продакшн Express-бэкенд.

### Коммитим в `master` без PR

Соло-разработка, PR добавил бы шаг ревью самой себя без реального смысла. Если подключится ещё один человек — вернуться к этому решению.

## Отменённые решения

**Точечный запрет на «обрубленные» фигуры в `prompts/visual-generator.md`** — добавлен и в тот же день отменён. Явный запрет сработал не так: на следующей генерации модель выбрала кадр с человеком, обрезанным по рту — не тот же класс брака, но явное последствие формулировки «не обязательно с лицом» как одного из разрешённых вариантов. Пользователь: «невозможно предусмотреть каждый косяк при генерации, чем больше ограничений, тем больше путаешь модель, смещая акценты». Промпт возвращён к прежнему состоянию.
