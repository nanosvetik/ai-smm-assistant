# Известные грабли

Реальные проблемы, на которые уже наступали в этом проекте. **Читать до отладки**, а не после — большая часть описанного выглядит как баг в своём коде, но им не является.

## Окружение и инструменты

- **Кириллица через `curl -d` в Git Bash на Windows — не доверять.** Прямой `curl -X POST... -d '{"text":"кириллица"}'` из Git Bash молча портит многобайтовые UTF-8 символы в аргументе командной строки ещё до отправки запроса (в БД долетают кракозябры) — артефакт консольной кодировки шелла, не баг бэкенда/фронтенда. Тот же запрос через настоящий `fetch` (Node-скрипт или браузер) идёт без потерь. Для живых тестов с русским текстом — писать тело запроса в `.mjs`-скрипте и гонять через `fetch`.
- **Windows + `taskkill //F` на фоновый Node-процесс:** может оставить `*.stackdump` в рабочей директории и не дать stdout-буферу сброситься на диск (недостающие строки лога — не всегда баг в коде, иногда просто буферизация). При отладке фоновых процессов проверять состояние через БД/реальный вызов API, а не только через лог.
- **`npm create vite@latest` подсовывает несовместимый стек.** Scaffold ставил Vite 8 на rolldown (нативные `.node`-биндинги) + React 19 + TS 6 — упало на `vite --version` с `Cannot find native binding`, несовместимо с Node v20.14.0 (пакеты требуют `^20.19`). Пересобрали `frontend/package.json` руками на пиновках, совместимых с `backend` (Vite 5, React 18, TypeScript ~5.6, `@vitejs/plugin-react` 4). Перед следующим `npm create vite`/аналогичными generator-командами — сначала проверять, что стек реально стартует (`npx vite --version`), не доверять дефолтам генератора.
- **`process.cwd()` в путях к данным — отложенная поломка деплоя.** Пока сервис запускают из `backend/`, пути от рабочей директории верны, и ошибка не проявляется вообще. Стоит запустить процесс иначе (systemd со своим `WorkingDirectory`, cron, `node backend/dist/index.js` из корня) — промпты не находятся, а SQLite ведёт себя хуже всех: `better-sqlite3` на несуществующем файле молча создаёт новый пустой, и сервис поднимается «успешно», без единого клиента и без сессий. Все пути считаются от расположения модуля — `backend/src/lib/paths.ts`, тест запускает его из посторонней директории. Побочное следствие того же класса: `dotenv.config()` вызывался только в `index.ts`, поэтому `npm run admin:approve` выдавал оператору ссылку `http://localhost:5173` и никогда не отправлял письмо. Теперь `.env` грузит `lib/loadEnv.ts` — первым импортом в каждой точке входа, а всё, что читает окружение при загрузке, подключается динамическим `import()` после него.
- **Пути к файлам на диске, которые попадут в публичный URL:** `path.relative` на Windows-деве отдаёт бэкслэши; прод — Linux с раздачей статики через nginx/Caddy, где бэкслэш ломает URL. Нормализовать на forward slashes (`.split(path.sep).join("/")`) перед сохранением в БД — см. `backend/src/routes/onboarding.ts`.
- **Windows-права на приватный SSH-ключ ломают вход по ключу молча-по-смыслу.** OpenSSH отказывается читать ключ (`UNPROTECTED PRIVATE KEY FILE`, дальше `Permission denied (publickey)`), если у файла есть разрешения для кого-то кроме владельца — а по умолчанию там сидят «Система», «Администраторы» и «Все». Выглядит как «сервер не принимает ключ», хотя до сервера дело не дошло. Лечится `icacls <ключ> /inheritance:r /grant:r "<домен>\<пользователь>:F"` плюс явное `/remove:g *S-1-5-18 /remove:g *S-1-5-32-544 /remove:g *S-1-1-0`. `Set-Acl` из PowerShell на этом файле падает (`ACL is not in canonical form`, затем `SeSecurityPrivilege`) — использовать `icacls`.
- **`js-yaml` под ESM:** `import yaml from "js-yaml"` компилируется без ошибок (`tsc` пропускает через `esModuleInterop`), но падает в рантайме — `does not provide an export named 'default'`. Использовать именованный импорт: `import { load } from "js-yaml"`.

## Drizzle и миграции

- **`drizzle-kit generate` требует настоящий TTY при неоднозначном diff** (например, одновременное удаление старых колонок и добавление новых в одной таблице — «это переименование или дроп+создание?») — падает `Error: Interactive prompts require a TTY terminal`, даже если пропихивать ответ через `printf... | npx drizzle-kit generate` (проверено: дело не в содержимом stdin, а в `isTTY`). В агентской среде это тупик — обходной путь:
 1. посмотреть текущий `meta/<N>_snapshot.json` (поля `id`/`prevId`/`tables.<table>.columns`);
 2. руками написать `meta/<N+1>_snapshot.json` (скопировать предыдущий, поправить таблицу, новый `id` через `crypto.randomUUID`, `prevId` = `id` предыдущего);
 3. написать SQL-файл миграции рядом (для SQLite drop+add колонок в `NOT NULL` без default — не построчный `ALTER TABLE ADD COLUMN`, а `DROP TABLE`+`CREATE TABLE` целиком между `PRAGMA foreign_keys=OFF/ON`);
 4. дописать запись в `meta/_journal.json`;
 5. `npm run db:migrate` применит как обычно, повторный `npm run db:generate` без TTY подтвердит совпадение (`No schema changes, nothing to migrate`).

 Пример — миграция `0019_normal_captain_flint.sql` (`visual_generator_prompts`).
- **Ручная запись `when` в `meta/_journal.json` может тихо отключить все последующие автосгенерированные миграции навсегда, без единой ошибки.** Мигратор drizzle-orm (`sqlite-core/dialect.js`) применяет только те миграции, у которых `folderMillis` (то самое `when`) больше `created_at` последней применённой строки в `__drizzle_migrations`; порядковый `idx` в журнале не участвует вообще. У `0019` `when` был вручную выставлен на круглое время в будущем — обе следующие миграции (`0020`, `0021`), сгенерированные обычным путём часом раньше по реальным часам, получили меньший `when` и молча пропускались, при бодром «Migrations applied» в выводе. **Правило:** при ручной правке журнала `when` обязан быть больше `when` последней реально применённой миграции, не просто «текущее время». После любой ручной правки — сверять `SELECT created_at FROM __drizzle_migrations ORDER BY created_at DESC LIMIT 1` до и после, и проверять `PRAGMA table_info(<table>)` на самом файле БД, не доверяя тексту в консоли.
- **`npm audit` на `drizzle-kit`:** стабильная `0.31.10` тянет уязвимый transitive `esbuild` (moderate, dev-server only, некритично для `generate`/`migrate`). Более новые `1.0.0-rc.*` ломаются об текущий `drizzle-orm` (`ERR_PACKAGE_PATH_NOT_EXPORTED`) — не апгрейдить туда без проверки совместимости.

## Парсинг документов агентов

- **`parseFrontmatter` ловил не тот блок `---`.** Модель иногда вставляет markdown-разделитель `---` в тело документа до настоящего YAML-frontmatter (например, перед ```` ```yaml ```` кодфенсом) — первая non-greedy пара `/---\s*\n([\s\S]*?)\n---/` захватывала произвольный кусок текста и валила `js-yaml`, молча роняя весь запуск агента. Исправлено: `backend/src/lib/frontmatter.ts` перебирает все пары строк `---` по порядку и берёт первую, которая реально парсится как YAML-объект.
- **Двоеточие внутри значения ломает весь YAML-frontmatter, не только это поле.** Поле `тема:` копирует тему дословно из контент-плана, а темы часто в формате «Формат: суть» — `js-yaml.load` кидает исключение на **всём** блоке. Оба места, полагающиеся на успешный `load` для валидации блока (`backend/src/lib/frontmatter.ts`, `frontend/src/lib/markdown.ts`), тихо решали «это не настоящий frontmatter»: бэкенд не мог подставить статус, фронтенд не срезал frontmatter вообще, сырой YAML утекал в интерфейс. Исправлено в обоих: если прямой `load` падает, пробуем ещё раз, автоматически взяв в кавычки значения, содержащие `:` (`quoteColonValues`/`isParsableFrontmatter` — только для валидации, сохранённый документ не переписывается). Промпты `copywriter.md`/`reels-writer.md` дополнительно просят квотировать `тема`.
 **Урок:** любое новое поле frontmatter, копирующее свободный текст откуда-то ещё (не жёсткий enum вроде `статус`/`платформа`), — источник этого же класса бага; закладывать `quoteColonValues`-паттерн сразу.
- **«Разбирается как YAML-объект» — слишком слабый признак frontmatter.** Обычный маркированный список разбирается в массив, то есть в объект: перечисление между двумя markdown-разделителями засчитывалось за frontmatter и вырезалось вместе с ними — из документа на странице результатов молча пропадал кусок текста. Прежний тест этого не ловил, потому что проверял документ с одним `---`, а одна строка пары не образует. Теперь массивы отбрасываются, а среди разобранных блоков выигрывает тот, где есть поля самих агентов (`тип`, `статус`, `создан`, `обновлён`, `платформа`); прежний разбор остался запасным вариантом. **Правило шире:** признак «структура распарсилась» почти всегда слабее признака «в структуре есть ожидаемые поля».
- **`\s*` в построчном regex переходит на следующую строку.** В `replaceFrontmatterField` шаблон `^поле:\s*\S+` на поле с пустым значением съедал перевод строки и затирал соседнее поле блока. Для «значение в этой же строке» — `[ \t]*[^\n]*$`, не `\s*`.
- **Модель может обернуть в кодфенс весь документ, а не только frontmatter.** `profile-header-analyzer` (Claude Sonnet 5) обернул всё в один ` ```markdown ` фенс — старый `stripFrontmatter` ждал только `yaml`/`yml` и фенс вплотную вокруг frontmatter, весь документ ушёл в блок кода. Исправлено: парсер принимает фенс с любым языком и, если закрывающий ` ``` ` не находится сразу после frontmatter, ищет его в конце документа. Промпт дополнен явным правилом.

## Внешние API

- **Telegram `allowed_updates`:** Telegram применяет ограничение типов апдейтов, заданное *первым в истории* вызовом `getUpdates` для этого бота — даже из прошлого, не связанного проекта. Без явного `allowed_updates: ["message", "callback_query"]` на каждый вызов кнопки могут молча не долетать, без единой ошибки. См. `backend/src/lib/telegram.ts`.
- **OpenRouter и экспериментальные/дешёвые модели:** запрос к `deepseek/deepseek-v4-flash-vision-exp` падал `404 No endpoints available matching your guardrail restrictions and data policy` — privacy-настройки аккаунта (`openrouter.ai/settings/privacy`) по умолчанию не разрешают маршрутизацию на провайдеров, обслуживающих такие модели (обычно требуют разрешение на обучение на входных данных). Разрешение сознательно не включали. Если понадобится другая экспериментальная/бесплатная модель — сначала проверять эту настройку, не считать 404 багом кода.
- **Информация об API OpenRouter устаревает быстрее, чем записи в этом файле.** Ограничение «референсные кадры для видео — только по публичному URL» (живой тест 2026-08-29) было верно для прежней плоской схемы (`first_frame_url`/`reference_image` как строки) и держало целую фичу отложенной до появления публичного домена. Оказалось, что появилась новая схема `frame_images[]`/`input_references[]` с той же обёрткой `{type:"image_url", image_url:{url}}`, что и в chat completions, и она принимает `data:`-URI. Перед тем как объявить фичу заблокированной внешним API — перепроверять доки/`/models` живым вызовом.
- **Google Fonts: дефолтные `curl`-запросы не содержат кириллицу.** Fraunces и Figtree (референсы из дизайн-брифа) **не имеют кириллицы вообще** — проверять `subsets` через `fonts.google.com/metadata/fonts` до скачивания файлов. Отдельно: даже у гарнитур с кириллицей (Alegreya, Golos Text) запрос к `fonts.googleapis.com/css2` без заголовка `Accept-Language: ru-RU` отдаёт только `latin`/`latin-ext` блоки.
- **multipart и кириллица в имени файла:** busboy (внутри `multer`) по умолчанию декодирует заголовки multipart как `latin1`, не `utf8` — кириллическое имя сохраняется кракозябрами. Общее лечение — `decodeOriginalFilename` в `lib/uploads.ts`, применяется в обоих эндпоинтах загрузки. Считалось латентным для онбординга («имя нигде не отображается») — на деле имя файла попадает в промпт распаковки аудитории и экспертности вместе с категорией референса, то есть кракозябры уходили в модель.
- **Категория загрузки — параметр маршрута, не multipart-поле:** порядок частей в multipart не гарантирован, к моменту `destination`-колбэка текстовое поле после файла может быть ещё не распаршено.
- **`undici` 7 не заводится на Node 20.14** — падает при импорте пакета, ещё до первого запроса: `TypeError: webidl.util.markAsUncloneable is not a function`. Метод появился в более поздних сборках Node 20. Закреплена `undici@^6.21.0`. Перед апгрейдом пакета, тесно завязанного на внутренности рантайма, — сверять его `engines` с реальной версией Node на дев-машине **и** на сервере, а не только с «Node 20».
- **Unisender Go: `skip_unsubscribe` доступен не всем аккаунтам.** Поле, отключающее блок «отписаться» (для транзакционных писем оно по смыслу правильное), принимается только от аккаунтов с флагом `allow_skip_unsubscribe`; остальным API отвечает `HTTP 400`, код `1588`, и письмо **не уходит вообще**. Флаг выдаёт поддержка по запросу. Ошибка ловится только живой отправкой: код компилируется, поле документировано, а тестовое письмо из панели ходит другим путём и ничего не проверяет. Общее правило для полей чужого API, помеченных как необязательные, — проверять живым вызовом с тем аккаунтом, который поедет в прод.
- **Адрес для следующего шага берётся из ответа на создание задачи и больше не перечитывается.** В генерации видео `polling_url` заново читался из каждого ответа опроса. Поле документировано для ответа на `POST /videos`; стоило очередному ответу его не повторить — и оплаченная задача Kling бросалась через пять секунд, хотя считается около минуты. Эталон — `smm-mcp/src/index.js`, где адрес захватывается один раз до цикла.
- **Шлюз-«замена OpenRouter» не годится для видео и медиа.** Схема «обращайся к совместимому шлюзу вместо провайдера» покрывает только chat completions. `/api/v1/images` и `/api/v1/videos` — собственные эндпоинты OpenRouter, в OpenAI-совместимый набор не входят. На видео ломается принципиально: генерация — это три обращения, и адреса для второго и третьего (`polling_url`, `unsigned_urls`) приходят **внутри ответа** и ведут на настоящий `openrouter.ai` и его хранилище — код идёт по ним как есть, мимо любого шлюза. Общее правило: подменять базовый адрес можно только там, где ответ не содержит абсолютных ссылок для следующего шага; во всех остальных случаях нужен прозрачный проксирующий выход, сохраняющий адреса.

- **Цена генерации зависит от того, что модель включила сама, а не только от заказанных параметров.** Kling v3.0 Pro стоит `$0.112` за секунду без звука и `$0.168` со звуком — это разные SKU в `pricing_skus`. Код звук не заказывает и не отключает (поля `generate_audio` в запросе нет вовсе), модель включает его по умолчанию, и пятисекундный клип обошёлся в `$0.84` вместо ожидаемых `$0.56` — в полтора раза дороже. Замечено только сверкой факта с расчётом: в ответе задачи цена приходит уже итоговая, а в файле нашлась звуковая дорожка (`SoundHandler` в `moov`). **Считая стоимость операции, смотреть на весь набор SKU модели, а не на одну строку цены**, и сверять расчёт с фактическим списанием после первого живого вызова. Закрыто явным `generate_audio: false` в запросе (параметр документирован, по умолчанию `true` у всех моделей со звуком). **Подтверждено живыми цифрами:** следующий клип обошёлся в `$0.56` против `$0.84`, звуковой дорожки в файле нет.
- **Оплаченная задача, адрес которой живёт только в памяти процесса, теряется целиком.** Генерация видео создаёт задачу (деньги списываются сразу), получает `polling_url` в ответе и опрашивает его в цикле. Стоило поллингу оборваться — таймаут, перезапуск службы, разрыв соединения, — и забрать оплаченный клип становилось нечем: у обычного ключа OpenRouter **нет ни списка задач** (`GET /api/v1/videos` → 404), **ни доступа к активности** (`/api/v1/activity` → 403, «only management keys»). Живой случай: клип с референсным кадром не уложился в 200 секунд, остался `pending`, и `$0.56` ушли впустую. Теперь адрес опроса пишется в журнал сразу после создания задачи и повторяется в тексте ошибки. **Общее правило: если внешняя операция платная, идентификатор оплаченного результата должен попасть в журнал раньше первого ожидания, а не только в переменную.**
- **Генерация видео с референсным первым кадром идёт в разы дольше текстовой — и не помещается в синхронный HTTP-запрос.** Клип без референса укладывался в 200 с; клип с референсом на той же модели считался **около десяти минут**. Задача при этом не ломается — она просто не успевает, и клиент получает ошибку за оплаченный результат, который сделается уже без него. Замер по одному наблюдению, роль конкретного файла (скриншот `430 × 497` с альфа-каналом при запрошенных `9:16` против сгенерированной картинки в нужной пропорции) не отделена. **Общий вывод, от файла не зависящий: время ожидания для image-to-video планировать отдельно от text-to-video, а операцию длиннее лимита рантайма — не держать внутри запроса от браузера.**
- **Долгая генерация внутри одного HTTP-запроса упирается в `requestTimeout` Node (300 с по умолчанию), а не в скорость модели.** Поэтому потолок ожидания клипа — 250 секунд: ждать дольше бессмысленно, соединение с браузером оборвётся раньше. Настоящее лечение — фоновая задача с опросом со стороны интерфейса; для MVP сознательно оставлен синхронный вызов с потолком под лимитом рантайма.
- **Успешный ответ почтового API — это не доставка до глаз человека.** Письмо со ссылкой на результаты уходило с `HTTP 200`, попадало в «Спам» и оставалось непрочитанным. Код при этом считал доставку состоявшейся (`delivered = true`) и не включал запасной путь «сообщить оператору, чтобы переслал вручную» — то есть отказ был беззвучным с обеих сторон: клиент не знал, что работа закончена, оператор не знал, что клиент не знает. Отсюда правило: **канал, попадание в который нельзя проверить, не может быть единственным** — результат должен быть доступен и там, где пользователь уже находится (в кабинете), а письмо остаётся дублем.

## Фронтенд

- **`react-markdown` не рисует GFM-таблицы без `remark-gfm`.** Из коробки только базовый CommonMark — таблицы из документов агентов рендерились строкой с символами `|`. Любой новый экран с markdown агентов — сразу подключать `remark-gfm`.
- **`react-markdown` рендерит код-фенсы как `<pre>` с браузерным дефолтом `white-space: pre`.** Агенты иногда оборачивают в безымянный фенс не код, а обычный текст (версии био у `account-packager`) — длинная строка вылезает за карточку вместо переноса, потому что у родителей `overflow-x: visible`. Нужно явное `pre { white-space: pre-wrap; overflow-wrap: anywhere; }` в CSS контейнера. Проверять на реалистичной (не полноэкранной) ширине окна.
- **Vite dev-прокси надо дополнять при каждом новом статическом пути.** `/uploads` забыли добавить рядом с `/api` и `/media` — браузер в деве стучался в сам Vite-сервер, `<img>` не получал картинку. Правка `vite.config.ts` требует, чтобы Vite перезапустил dev-сервер (обычно делает сам, но проверять).
- **`z-index: auto` проигрывает соседу с явным положительным `z-index`, независимо от DOM-порядка.** `.sidebar-backdrop` с `z-index: 15` перехватывал клики поверх списка меню без своего `z-index` — визуально был позади, кликами впереди.
- **Специфичность CSS, а не порядок в файле.** `.onboarding-success p { color: var(--color-muted) }` (0,1,1) перебивало `.onboarding-success-note { color: var(--color-text) }` (0,1,0) — текст оставался нечитаемым. Лечится удлинением селектора (`.onboarding-success.onboarding-success-note`, (0,2,0)), не `!important`.
- **Смена этапа в SPA не сбрасывает скролл** — новый документ мог открываться с середины. Явный `window.scrollTo(0, 0)` в обработчике выбора.
- **Крупный декоративный глиф позади текста (`position: absolute`) наезжает на буквы** — читается как визуальный мусор. Класть в нормальном потоке рядом с текстом (`flex`), а не накладывать позади.
- **Идемпотентность «по факту созданной записи» превращает разовый сбой доставки в потерю навсегда.** `ensureResultsLinkSent` создаёт ссылку, потом шлёт письмо, а на входе выходит сразу, если ссылка уже есть. Непойманная ошибка `sendMail` означала, что письмо не ушло, повторной попытки не будет никогда (ссылка-то создана), а вызывающий код глотает ошибки — fire-and-forget. Правило: если функция идемпотентна по побочному эффекту, всё, что происходит **после** создания этого эффекта, обязано иметь свой перехват и запасной путь.
- **Проверка-и-запись в две операции — это гонка, даже без параллельных процессов.** Тот же `ensureResultsLinkSent`: между «ссылки нет» и `insert` укладывается второй вызов, который прошёл ту же проверку. Клиент, догенерировавший последний пост в двух вкладках, получал два письма с двумя разными ссылками на 90 дней. Закрыто очередью по клиенту в памяти процесса (сервис однопроцессный, см. `docs/decision-log.md`); при переходе на несколько процессов понадобится уникальный индекс на `(client_id, kind)`. Тест воспроизводит гонку: без очереди он падает на второй созданной ссылке.
- **Один `Promise.all` на всю загрузку экрана превращает частный сбой в «ничего нет».** В кабинете результаты девяти этапов читались одним `Promise.all`; одна неудачная выдача роняла всё, состояние оставалось пустым, и экран честно рисовал «Пока не запускали» с кнопкой запуска — приглашение оплатить заново уже сделанное. Правило: при загрузке независимых кусков ошибку ловить у каждого, а в модели данных различать «нет результата» и «не удалось узнать» — иначе интерфейс уверенно врёт про пустоту.
- **Загрузочный эффект без `.catch` прячет компонент целиком.** Паттерн `useEffect(() => { load().then(() => setLoaded(true)) })` вместе с `if (!isLoaded) return null` при любой ошибке оставляет `null` навсегда: блок исчезает вместе со своей кнопкой, и этап выглядит завершённым. Для блоков, за которыми стоит платная операция, это ещё и риск оплатить второй файл поверх готового.
- **`navigator.clipboard` существует только в защищённом контексте.** По https и на localhost есть, по http с адреса сервера — нет вовсе, плюс вызов отклоняется, если вкладка потеряла фокус. Нужен запасной путь через `execCommand("copy")` и возврат признака успеха: иначе кнопка показывает «Скопировано» там, где буфер пуст.
- **`URL.revokeObjectURL` сразу после `link.click()` обрывает скачивание.** Firefox и Safari отменяют уже начавшуюся загрузку, если объектный URL освободить в том же кадре; часть браузеров вдобавок игнорирует клик по ссылке вне DOM. Общий `downloadBlob` (`lib/download.ts`) добавляет ссылку в документ и откладывает отзыв.
- **`.every` на пустом массиве вакуумно возвращает `true`.** `isDone` для площадочных этапов показывал галочку «пройдено» у клиента без единой своей ссылки. Правило: если список площадок пуст — это не прохождение, проверять `length === 0` явно до `.every`.
- **`res.json` падает на пустом теле ответа.** `DELETE`-запросы через общую обёртку `request` в `api.ts` в принципе не могли отработать, пока она не научилась возвращать `undefined` на `204 No Content`.
- **`null` из БД утекает в состояние формы и в шаблонную строку.** Новая колонка анкеты (`expertPath`) у старых клиентов приходит как `null`; спред `{...defaults,...state.questionnaire}` не спасает — ключ с явным `null` перекрывает `""`-дефолт. Дальше `!value.trim` кидал необработанное исключение **вне** `try/catch`, и форма молча ничего не отправляла. Второй слой: `${null}` в JS-темплейте рендерится строкой `"null"` и уезжает в промпт — коалесить (`?? "не предоставлено"`) на стороне агента тоже.

## Промпты и поведение моделей

- **Утечка внутренней механики промпта в тело документа.** Модели пересказывали свои же шаги («диагностика по Шагу 1.3», «прежде чем выдать документ, важные технические замечания»), копировали служебные названия («Уровень осознанности **по Ханту**»), дублировали заголовок раздела с его же bold-лидом. Причина обычно — двусмысленная формулировка в самом промпте (название пункта структуры ≠ заголовок вывода). Правило для новых промптов: пункт структуры называет **точный** заголовок вывода, пример-цитата под ним без своего лида, плюс явный запрет ссылаться на номера фаз/шагов/блоков где-либо в теле документа.
- **Запрет, названный через конкретный объект, модель выполнит буквально и обойдёт по смыслу.** Правило «не добавляй новый текст» было написано в расчёте на кадр, поверх которого не надо ничего дописывать. `reels-video-generator` выполнил его дословно и обошёл: отодвинул стартовый кадр в угол, подложил под него экран телефона, которого на кадре нет, и попросил набрать на нём две фразы по буквам — с честной оговоркой «на исходном коллаже нового текста нет». Формулировать запрет по существу нежелательного (никаких новых читаемых букв нигде в клипе), а не по одному месту, где их не ждали.
- **Ужесточая запрет, сразу очерчивай его границу — иначе модель распространит его шире и начнёт себе противоречить.** Тот же промпт после ужесточения выдал «искры мягко мерцают» и следом «всё остаётся неподвижным»: запрет писался про буквы, а модель применила его ко всей графике кадра. Границу («замораживаются буквы, нетекстовые элементы двигаться могут») пришлось дописывать отдельным абзацем. Проверять такие правки живым прогоном, а не чтением — противоречие видно только в выводе.
- **Блок «Следующий шаг» — только фиксированный текст.** DeepSeek приклеивал к шаблонному тексту собственную содержательную оговорку одним абзацем без разделения. Во всех промптах с этим блоком явно написано «ничего от себя — оговорки в разделы выше».
- **Не называть в документах внутренние имена агентов/инструментов** (`account-packager`, `generate_image`) — клиент их не знает. Ссылаться на название следующего **документа** («идёт в `Упаковку профиля`») или на результат простым языком.
- **DeepSeek воспроизводит инструкцию дословно там, где Claude додумывает.** Один и тот же двусмысленный кусок промпта у Sonnet работал годами, а на DeepSeek дал дубль заголовка. Тестировать промпт на той модели, на которой он реально поедет.
- **Код считает ссылки, модель считает сущности — и в шапке документа нужна вторая цифра.** Клиент указал три ссылки на конкурентов, но конкурентов было двое: у одного магазина и Telegram, и ВК. Модель это поняла и написала «конкурентов_проанализировано: 2», а код в колонке `competitorsAnalyzed` хранит `competitorLinks.length` = 3. Расхождение выглядит как ошибка модели, но ошибается здесь код: свести две площадки в одного владельца — это суждение по содержимому, а не арифметика, и коду оно недоступно. **Прежде чем «чинить» цифру из документа подстановкой из кода, проверять, что код считает то же самое понятие.** Даты — считает (документ создан сегодня, и это факт); число разобранных сущностей — нет.
- **Каждая ветка отказа в промпте должна отдельно проговаривать, что делать в автономном режиме.** Мало объявить режим автономным один раз в начале: пороги и хард-стопы, написанные под живой диалог, продолжают срабатывать. В `expertise.md` порог «≥30% ответов пустые — остановись» считал пробелами всё, о чём в анкете просто не спрашивали, и предлагал провести интервью — а собеседника в продукте нет вовсе. Проверять надо каждую ветку по отдельности: перечитать все места, где промпт останавливается или просит дослать данные, и написать для автономного режима альтернативу. Альтернатива почти всегда одна: выдать документ с пониженным статусом, пометками о пробелах и перечнем, чего не хватило, — потому что человек нажал кнопку и ждёт результат, а не переписку.
- **Заголовок раздела во входных данных — это обещание модели.** Раздел назывался «Свои соцсети (материалы про эксперта)», а под ним были только адреса каналов: открыть их модель не может. При инструкции «не ссылайся на то, чего не видел» это прямо ведёт к выводу «материалов нет» и к отказу. Либо в разделе лежит то, что заявлено заголовком, либо заголовок называет вещи своими именами.
- **Смена модели переоценивает каждую строгую формулировку в промпте.** Фраза «работаешь только с экспертами» стояла в `target-audience.md` изначально, и на DeepSeek прогоны шли нормально: он читал её как настройку тона. Sonnet, поставленный вместо него, исполнил её как правило допуска и отказался работать с товарным бизнесом — при том что продукт заявлен и для мелкого бизнеса тоже. Формулировки, которые прежняя модель обходила, новая исполняет буквально, поэтому **смена модели агента — это не замена детали, а повод перечитать его промпт целиком и прогнать вживую до выкладки**. Особенно опасны условия допуска и отказа: они срабатывают на первом же клиенте и выглядят для него как «вы нам не подходите».
- **Модель может застрять в интерактивном режиме.** `expertise.md` не содержал форс-автономного режима (в отличие от `target-audience.md`) — модель выбирала интерактивный диалог и сохраняла как финальный документ «Вопрос 1 (Блок 1)…». Код это не ловил: `parseFrontmatter` тихо возвращал `null`, подставлялся дефолтный статус. Любой промпт, у которого в тексте есть ветки «спросить эксперта», обязан содержать явное «для этого продукта режим всегда автономный».
- **Числовой порог статуса — это пол, а не потолок.** В `visual-style-analyzer` код ставил `статус: боевой` по правилу «3+ референса», не читая, что модель написала о согласованности — а она прямо в теле документа просила не считать профиль боевым. Правило: счётчик может принудительно **занизить** статус при нехватке данных, но не завышать поверх честной самооценки модели.
- **Не добавлять точечные защитные формулировки в промпты генерации изображений реактивно.** Явный запрет на «обрубленные фигуры» привёл к тому, что модель выбрала кадр с человеком, обрезанным по рту — новый, не лучший результат. Правку отменили целиком. Чем больше ограничений, тем сильнее смещаются акценты модели; риск перевешивает пользу от исправления одного случая.
- **Модель обобщает именованные сущности, если не запретить.** `reels-video-generator` превратил «Тандзиро из „Клинка, рассекающего демонов“» в «anime figure with a sword» — видео-модель имени вообще не видела. Промпт теперь требует сохранять узнаваемые визуальные детали именованных персонажей/товаров.
- **Модель честно откажется натягивать несвязанные факты.** `account-packager` отказался сверять рекомендации с «Аудитом шапки профиля», когда в аудите оказались чужие тестовые каналы, — это защита, а не баг, но она означает, что «путь совпадения» на тестовых данных не проверяется. Такие ветки проверяются только на реальном клиенте.

- **Запрет в промпте не отменяет задания, которое его требует.** `reels-video-generator` обязан писать промпт без текста в кадре («большинство видео-моделей плохо рендерят читаемый текст») — и честно приписал `No readable text appears on screen`. Но хук сценария был построен вокруг экрана телефона, поэтому тот же промпт заказал чат с названием магазина, аватаркой и пузырями сообщений. Интерфейс без букв не рисуется: Kling заполнил его псевдотекстом. **Ограничение работает, только если оно совместимо с сюжетом**; когда сюжет требует запрещённого, промпту нужна не строчка запрета, а ветка «уйти на другой план» — предметный кадр, руки, реакция человека. Проверять такие пары «задание + запрет» на самом неудобном входе, а не на удобном.
- **Модель пишет в текст промпта параметры, которыми она не управляет.** Тот же документ содержал `3 seconds duration`, хотя длительность задаёт код и всегда просит 5 секунд. На результат не повлияло (параметр запроса сильнее текста), но документ противоречит сам себе, и при чтении глазами это выглядит как настройка, которой на деле нет. Полезно либо запрещать модели упоминать длительность/формат, либо подставлять туда фактические значения кодом.

## Проектирование под неполные данные

- **Не считать, что у клиента обе площадки.** `content-planner` был написан с жёстким предположением «есть и Telegram, и ВК», хотя форма разрешает 0–2 own-ссылки. Площадки берутся из `social_links` (role=own), **не** из `account_style_profiles.platforms` (там площадка могла выпасть, если парсер не нашёл постов, хотя клиент её указал). `copywriter` дополнительно падает `PlatformNotInPlanError`, если запрошенной площадки нет в плане. Reels существуют только для ВК.
- **Убрать из интерфейса запись в таблицу — значит молча обрезать вход агенту, который из неё читает.** Форму загрузки референсов перенесли в другое место кабинета и в новую таблицу; старую оставили «нетронутой», а `visual-style-analyzer` продолжал читать именно её. Ошибки при этом не бывает никогда: таблица существует, запрос отрабатывает, просто возвращает пусто — агент штатно сообщает «референсов нет» и возвращает `undefined`, потребитель штатно работает без профиля. Снаружи выглядит как «клиенты почему-то не грузят фото», и **дефект прожил девять дней**, пока не полезли разбираться с другим симптомом. Проверять такую ветку счётчиком строк на боевом (`select count(*)`), а не чтением кода: код-то читается ровно так, как задумано. **Правило:** переезд данных в новую таблицу не закончен, пока не перечислены все читатели старой и для каждого не решено явно — переключить или признать мёртвым.
- **Два места, независимо выбирающих «самую свежую запись», рано или поздно выберут разные.** Стартовый кадр клипа брали тремя отдельными запросами `order by created_at desc limit 1`, а время хранится с точностью до секунды: клиент выбирает несколько файлов разом, два попадают в одну секунду, и дальше порядок задаёт SQLite — совпадать между запросами он не обязан. Симптом был бы издевательский: промпт добросовестно описывает один кадр, видео начинается с другого, и всё это без единой ошибки. Лечится не проверкой, а структурно: одна общая функция выборки плюс второй ключ сортировки (`id`), чтобы порядок был полным. **Правило:** если «последняя запись» нужна больше чем одному читателю, это не запрос, а общая функция; и сортировка по времени с точностью до секунды — не полный порядок.
- **Ленивое кэширование живёт ровно до тех пор, пока живо предположение о неизменности входа.** `ensureVisualStyleProfile` не пересчитывала профиль никогда — «референсы грузятся один раз на онбординге, измениться не могут». После переезда на референсы рилса, которые добавляют и удаляют прямо перед генерацией, та же строчка кода стала означать «показывать стиль фотографий, которых у клиента больше нет». Условие кэша стоит писать рядом с кэшем словами: когда предположение отменят, комментарий заметят, а молчаливое `if (existing) return existing` — нет.

## Серверы и деплой

Конкретика по машинам проекта (адреса, доступы, что открыто) — в `docs/infrastructure.local.md`, он не в репозитории: репозиторий публичный.

- **Живые правила iptables и сохранённые — разные вещи.** `iptables -I...` меняет только то, что действует сейчас; файл, из которого правила восстанавливаются при загрузке, сам не обновляется. Расхождение молчит до первой перезагрузки, а потом выглядит как беспричинная поломка сервиса — искать будут где угодно, только не в фаерволе. После любой правки — `netfilter-persistent save`, и `iptables-restore --test <файл>` перед тем, как файлу доверять: он разбирает файл ровно так же, как загрузка, но ничего не применяет.
- **`DROP` по порту без `-i <внешний интерфейс>` рубит исходящие соединения контейнеров.** Цепочка `DOCKER-USER` фильтрует `FORWARD`, а это не только входящие к контейнерам, но и их собственные обращения наружу. Правило «запретить всё на 443» без привязки к внешней сетевой карте закрывает не чужих, а свои же вызовы к любому HTTPS-API — то есть глушит именно то, ради чего сервер стоит.
- **В `DOCKER-USER` порт назначения проверяется через `--ctorigdstport`, а не `--dport`.** Docker подменяет адрес назначения раньше этой цепочки, `--dport` там просто не совпадёт.
- **`DOCKER-USER` покрывает только опубликованные Docker-порты, и только те, для которых правило написано.** Запрет для одного порта не распространяется на остальные: любой другой контейнер, опубликовавший порт, оказывается доступен из интернета (у нас так вышло с панелью Portainer). Сервисы самого хоста, например `sshd`, эта цепочка не касается вовсе — они фильтруются в `INPUT`.
- **Разворачивали от root, служба работает от другого пользователя — обновление кода сломается, но не сразу.** Первая выкладка (клон, установка, сборка) прошла от `root`, потом владельца сменили выборочно: верхние каталоги стали принадлежать служебному пользователю, а `.git/objects` и полторы сотни других путей остались за root. Работе это не мешало — служба только читает. Обнаружилось на первом же `git pull` от служебного пользователя: `insufficient permission for adding an object to repository database`. Лечится одним `chown -R` на весь каталог приложения; правило — после выкладки приводить владельца всего дерева к тому пользователю, от которого потом будут обновления, и проверять `find <каталог> ! -user <служебный> | wc -l`.
- **Доступность внешних сервисов проверять с самого целевого сервера, а не рассуждениями.** Одна серия `curl` с боевой машины закрыла все предположения о том, что откуда видно, — и заодно вскрыла нерабочий SMTP, о котором думали, что он на проде заработает. Делать это **до** проектирования обходных путей, а не после.
- **`403` и таймаут — разные диагнозы, не путать.** Быстрый `403` означает, что сеть пропускает и отказывает сам сервис (геоблок на его стороне) — лечится сменой точки выхода. Таймаут означает, что соединение не устанавливается вовсе (режут по дороге) — тут не поможет ни ключ, ни заголовки. По времени ответа видно сразу: отказ сервиса приходит за десятые доли секунды, блокировка — это ожидание до таймаута.
- **Прокси, подключённый через `dispatcher`, молча игнорируется, если что-то не так с типами или версией** — запрос просто уходит напрямую, и на дев-машине это выглядит как успех. Проверять надо **отрицанием**: с машины, которой к прокси доступ закрыт, вызов через него обязан провалиться. Если он проходит — значит прокси не применяется. Проверка «работает без прокси» о проде не говорит ничего.
- **`INPUT ACCEPT` по умолчанию означает, что любой новый слушающий порт открыт всему интернету.** Ставя на сервер что-то, что слушает сеть (прокси, панель, БД), правило-ограничение писать **в том же заходе**, а не «потом»: открытый форвард-прокси находят сканерами за часы и начинают гонять через него чужой трафик. Ограничение по адресу-источнику и пароль — независимые слои, ставить оба.
- **Прерванный шаг настройки оставляет полуфабрикат, неотличимый от готового результата.** Настройка сервера — это обычно цепочка «создать файл → разметить → включить → прописать в автозагрузку», и остановка посередине оставляет ровно те следы, по которым потом решают, что шаг сделан. Живой случай: своп-файл был создан, права выставлены, строка в `/etc/fstab` дописана — но `mkswap` не выполнялся, файл остался типом `data`, и система при каждой загрузке ссылалась в `fstab` на невалидный своп, оставаясь вовсе без него. Проверять надо **работающее состояние, а не наличие файлов**: `swapon --show` и `swaplabel`, `systemctl is-enabled`, живой запрос к сервису. И повторный прогон шага писать так, чтобы он сначала смотрел на фактическое состояние и останавливался при несовпадении, а не затирал вслепую.
- **Перезагрузку сервера проверять сразу после настройки, а не выяснять случайно.** Всё настроенное вручную — своп, службы, правила фильтрации — живёт в двух состояниях: действующем сейчас и записанном для следующей загрузки, и расхождение между ними ничем себя не выдаёт. Единственная честная проверка — перезагрузиться и посмотреть, что поднялось само. Пока сервисом никто не пользуется, это стоит минуты; после запуска такой возможности уже нет, и первая перезагрузка случится в худший момент.
- **Веб-консоль VDSina портит длинные вставки:** обрезает строки и теряет перевод строки между соседними командами, склеивая две в одну (`... >> /root/kecho -n '...'`). Длинные значения собирать по кускам в черновой файл и проверять длину `wc -c` до того, как использовать. Признак склейки — приглашение `>` вместо обычного: оболочка ждёт продолжения незакрытой команды, лечится `Ctrl+C`.

## Живые тесты

- **Одноразовый magic-токен, использованный тестовым скриптом, недоступен пользователю.** Скрипт, получающий сессию через `GET /api/access/:token`, сжигает ту же ссылку, которую потом нельзя отдать живому человеку. Для таких сценариев генерировать пользователю отдельный второй `access_links`-токен на того же `client_id`.
- **Playwright MCP `browser_snapshot` разворачивает `<details>`** — побочный эффект чтения accessibility-дерева, не баг страницы. Проверять `details.open` прямым `browser_evaluate` сразу после навигации.
