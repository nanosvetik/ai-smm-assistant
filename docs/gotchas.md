# Известные грабли

Реальные проблемы, на которые уже наступали в этом проекте. **Читать до отладки**, а не после — большая часть описанного выглядит как баг в своём коде, но им не является.

## Окружение и инструменты

- **Кириллица через `curl -d` в Git Bash на Windows — не доверять.** Прямой `curl -X POST ... -d '{"text":"кириллица"}'` из Git Bash молча портит многобайтовые UTF-8 символы в аргументе командной строки ещё до отправки запроса (в БД долетают кракозябры) — артефакт консольной кодировки шелла, не баг бэкенда/фронтенда. Тот же запрос через настоящий `fetch()` (Node-скрипт или браузер) идёт без потерь. Для живых тестов с русским текстом — писать тело запроса в `.mjs`-скрипте и гонять через `fetch`.
- **Windows + `taskkill //F` на фоновый Node-процесс:** может оставить `*.stackdump` в рабочей директории и не дать stdout-буферу сброситься на диск (недостающие строки лога — не всегда баг в коде, иногда просто буферизация). При отладке фоновых процессов проверять состояние через БД/реальный вызов API, а не только через лог.
- **`npm create vite@latest` подсовывает несовместимый стек.** Scaffold ставил Vite 8 на rolldown (нативные `.node`-биндинги) + React 19 + TS 6 — упало на `vite --version` с `Cannot find native binding`, несовместимо с Node v20.14.0 (пакеты требуют `^20.19`). Пересобрали `frontend/package.json` руками на пиновках, совместимых с `backend` (Vite 5, React 18, TypeScript ~5.6, `@vitejs/plugin-react` 4). Перед следующим `npm create vite`/аналогичными generator-командами — сначала проверять, что стек реально стартует (`npx vite --version`), не доверять дефолтам генератора.
- **Пути к файлам на диске, которые попадут в публичный URL:** `path.relative()` на Windows-деве отдаёт бэкслэши; прод — Linux с раздачей статики через nginx/Caddy, где бэкслэш ломает URL. Нормализовать на forward slashes (`.split(path.sep).join("/")`) перед сохранением в БД — см. `backend/src/routes/onboarding.ts`.
- **`js-yaml` под ESM:** `import yaml from "js-yaml"` компилируется без ошибок (`tsc` пропускает через `esModuleInterop`), но падает в рантайме — `does not provide an export named 'default'`. Использовать именованный импорт: `import { load } from "js-yaml"`.

## Drizzle и миграции

- **`drizzle-kit generate` требует настоящий TTY при неоднозначном diff** (например, одновременное удаление старых колонок и добавление новых в одной таблице — «это переименование или дроп+создание?») — падает `Error: Interactive prompts require a TTY terminal`, даже если пропихивать ответ через `printf ... | npx drizzle-kit generate` (проверено: дело не в содержимом stdin, а в `isTTY`). В агентской среде это тупик — обходной путь:
  1. посмотреть текущий `meta/<N>_snapshot.json` (поля `id`/`prevId`/`tables.<table>.columns`);
  2. руками написать `meta/<N+1>_snapshot.json` (скопировать предыдущий, поправить таблицу, новый `id` через `crypto.randomUUID()`, `prevId` = `id` предыдущего);
  3. написать SQL-файл миграции рядом (для SQLite drop+add колонок в `NOT NULL` без default — не построчный `ALTER TABLE ADD COLUMN`, а `DROP TABLE`+`CREATE TABLE` целиком между `PRAGMA foreign_keys=OFF/ON`);
  4. дописать запись в `meta/_journal.json`;
  5. `npm run db:migrate` применит как обычно, повторный `npm run db:generate` без TTY подтвердит совпадение (`No schema changes, nothing to migrate`).

  Пример — миграция `0019_normal_captain_flint.sql` (`visual_generator_prompts`).
- **Ручная запись `when` в `meta/_journal.json` может тихо отключить все последующие автосгенерированные миграции навсегда, без единой ошибки.** Мигратор drizzle-orm (`sqlite-core/dialect.js`) применяет только те миграции, у которых `folderMillis` (то самое `when`) больше `created_at` последней применённой строки в `__drizzle_migrations`; порядковый `idx` в журнале не участвует вообще. У `0019` `when` был вручную выставлен на круглое время в будущем — обе следующие миграции (`0020`, `0021`), сгенерированные обычным путём часом раньше по реальным часам, получили меньший `when` и молча пропускались, при бодром «Migrations applied» в выводе. **Правило:** при ручной правке журнала `when` обязан быть больше `when` последней реально применённой миграции, не просто «текущее время». После любой ручной правки — сверять `SELECT created_at FROM __drizzle_migrations ORDER BY created_at DESC LIMIT 1` до и после, и проверять `PRAGMA table_info(<table>)` на самом файле БД, не доверяя тексту в консоли.
- **`npm audit` на `drizzle-kit`:** стабильная `0.31.10` тянет уязвимый transitive `esbuild` (moderate, dev-server only, некритично для `generate`/`migrate`). Более новые `1.0.0-rc.*` ломаются об текущий `drizzle-orm` (`ERR_PACKAGE_PATH_NOT_EXPORTED`) — не апгрейдить туда без проверки совместимости.

## Парсинг документов агентов

- **`parseFrontmatter` ловил не тот блок `---`.** Модель иногда вставляет markdown-разделитель `---` в тело документа до настоящего YAML-frontmatter (например, перед ```` ```yaml ```` кодфенсом) — первая non-greedy пара `/---\s*\n([\s\S]*?)\n---/` захватывала произвольный кусок текста и валила `js-yaml`, молча роняя весь запуск агента. Исправлено: `backend/src/lib/frontmatter.ts` перебирает все пары строк `---` по порядку и берёт первую, которая реально парсится как YAML-объект.
- **Двоеточие внутри значения ломает весь YAML-frontmatter, не только это поле.** Поле `тема:` копирует тему дословно из контент-плана, а темы часто в формате «Формат: суть» — `js-yaml.load()` кидает исключение на **всём** блоке. Оба места, полагающиеся на успешный `load()` для валидации блока (`backend/src/lib/frontmatter.ts`, `frontend/src/lib/markdown.ts`), тихо решали «это не настоящий frontmatter»: бэкенд не мог подставить статус, фронтенд не срезал frontmatter вообще, сырой YAML утекал в интерфейс. Исправлено в обоих: если прямой `load()` падает, пробуем ещё раз, автоматически взяв в кавычки значения, содержащие `:` (`quoteColonValues`/`isParsableFrontmatter` — только для валидации, сохранённый документ не переписывается). Промпты `copywriter.md`/`reels-writer.md` дополнительно просят квотировать `тема`.
  **Урок:** любое новое поле frontmatter, копирующее свободный текст откуда-то ещё (не жёсткий enum вроде `статус`/`платформа`), — источник этого же класса бага; закладывать `quoteColonValues`-паттерн сразу.
- **Модель может обернуть в кодфенс весь документ, а не только frontmatter.** `profile-header-analyzer` (Claude Sonnet 5) обернул всё в один ` ```markdown ` фенс — старый `stripFrontmatter` ждал только `yaml`/`yml` и фенс вплотную вокруг frontmatter, весь документ ушёл в блок кода. Исправлено: парсер принимает фенс с любым языком и, если закрывающий ` ``` ` не находится сразу после frontmatter, ищет его в конце документа. Промпт дополнен явным правилом.

## Внешние API

- **Telegram `allowed_updates`:** Telegram применяет ограничение типов апдейтов, заданное *первым в истории* вызовом `getUpdates` для этого бота — даже из прошлого, не связанного проекта. Без явного `allowed_updates: ["message", "callback_query"]` на каждый вызов кнопки могут молча не долетать, без единой ошибки. См. `backend/src/lib/telegram.ts`.
- **OpenRouter и экспериментальные/дешёвые модели:** запрос к `deepseek/deepseek-v4-flash-vision-exp` падал `404 No endpoints available matching your guardrail restrictions and data policy` — privacy-настройки аккаунта (`openrouter.ai/settings/privacy`) по умолчанию не разрешают маршрутизацию на провайдеров, обслуживающих такие модели (обычно требуют разрешение на обучение на входных данных). Разрешение сознательно не включали. Если понадобится другая экспериментальная/бесплатная модель — сначала проверять эту настройку, не считать 404 багом кода.
- **Информация об API OpenRouter устаревает быстрее, чем записи в этом файле.** Ограничение «референсные кадры для видео — только по публичному URL» (живой тест 2026-08-29) было верно для прежней плоской схемы (`first_frame_url`/`reference_image` как строки) и держало целую фичу отложенной до появления публичного домена. Оказалось, что появилась новая схема `frame_images[]`/`input_references[]` с той же обёрткой `{type:"image_url", image_url:{url}}`, что и в chat completions, и она принимает `data:`-URI. Перед тем как объявить фичу заблокированной внешним API — перепроверять доки/`/models` живым вызовом.
- **Google Fonts: дефолтные `curl`-запросы не содержат кириллицу.** Fraunces и Figtree (референсы из дизайн-брифа) **не имеют кириллицы вообще** — проверять `subsets` через `fonts.google.com/metadata/fonts` до скачивания файлов. Отдельно: даже у гарнитур с кириллицей (Alegreya, Golos Text) запрос к `fonts.googleapis.com/css2` без заголовка `Accept-Language: ru-RU` отдаёт только `latin`/`latin-ext` блоки.
- **multipart и кириллица в имени файла:** busboy (внутри `multer`) по умолчанию декодирует заголовки multipart как `latin1`, не `utf8` — кириллическое имя сохраняется кракозябрами. Лечится `Buffer.from(req.file.originalname, "latin1").toString("utf8")` перед сохранением (сделано в `reelsReferences.ts`; латентно живёт в старом `onboarding.ts`, где имя нигде не отображается).
- **Категория загрузки — параметр маршрута, не multipart-поле:** порядок частей в multipart не гарантирован, к моменту `destination`-колбэка текстовое поле после файла может быть ещё не распаршено.

## Фронтенд

- **`react-markdown` не рисует GFM-таблицы без `remark-gfm`.** Из коробки только базовый CommonMark — таблицы из документов агентов рендерились строкой с символами `|`. Любой новый экран с markdown агентов — сразу подключать `remark-gfm`.
- **`react-markdown` рендерит код-фенсы как `<pre>` с браузерным дефолтом `white-space: pre`.** Агенты иногда оборачивают в безымянный фенс не код, а обычный текст (версии био у `account-packager`) — длинная строка вылезает за карточку вместо переноса, потому что у родителей `overflow-x: visible`. Нужно явное `pre { white-space: pre-wrap; overflow-wrap: anywhere; }` в CSS контейнера. Проверять на реалистичной (не полноэкранной) ширине окна.
- **Vite dev-прокси надо дополнять при каждом новом статическом пути.** `/uploads` забыли добавить рядом с `/api` и `/media` — браузер в деве стучался в сам Vite-сервер, `<img>` не получал картинку. Правка `vite.config.ts` требует, чтобы Vite перезапустил dev-сервер (обычно делает сам, но проверять).
- **`z-index: auto` проигрывает соседу с явным положительным `z-index`, независимо от DOM-порядка.** `.sidebar-backdrop` с `z-index: 15` перехватывал клики поверх списка меню без своего `z-index` — визуально был позади, кликами впереди.
- **Специфичность CSS, а не порядок в файле.** `.onboarding-success p { color: var(--color-muted) }` (0,1,1) перебивало `.onboarding-success-note { color: var(--color-text) }` (0,1,0) — текст оставался нечитаемым. Лечится удлинением селектора (`.onboarding-success .onboarding-success-note`, (0,2,0)), не `!important`.
- **Смена этапа в SPA не сбрасывает скролл** — новый документ мог открываться с середины. Явный `window.scrollTo(0, 0)` в обработчике выбора.
- **Крупный декоративный глиф позади текста (`position: absolute`) наезжает на буквы** — читается как визуальный мусор. Класть в нормальном потоке рядом с текстом (`flex`), а не накладывать позади.
- **`.every()` на пустом массиве вакуумно возвращает `true`.** `isDone()` для площадочных этапов показывал галочку «пройдено» у клиента без единой своей ссылки. Правило: если список площадок пуст — это не прохождение, проверять `length === 0` явно до `.every()`.
- **`res.json()` падает на пустом теле ответа.** `DELETE`-запросы через общую обёртку `request()` в `api.ts` в принципе не могли отработать, пока она не научилась возвращать `undefined` на `204 No Content`.
- **`null` из БД утекает в состояние формы и в шаблонную строку.** Новая колонка анкеты (`expertPath`) у старых клиентов приходит как `null`; спред `{...defaults, ...state.questionnaire}` не спасает — ключ с явным `null` перекрывает `""`-дефолт. Дальше `!value.trim()` кидал необработанное исключение **вне** `try/catch`, и форма молча ничего не отправляла. Второй слой: `${null}` в JS-темплейте рендерится строкой `"null"` и уезжает в промпт — коалесить (`?? "не предоставлено"`) на стороне агента тоже.

## Промпты и поведение моделей

- **Утечка внутренней механики промпта в тело документа.** Модели пересказывали свои же шаги («диагностика по Шагу 1.3», «прежде чем выдать документ, важные технические замечания»), копировали служебные названия («Уровень осознанности **по Ханту**»), дублировали заголовок раздела с его же bold-лидом. Причина обычно — двусмысленная формулировка в самом промпте (название пункта структуры ≠ заголовок вывода). Правило для новых промптов: пункт структуры называет **точный** заголовок вывода, пример-цитата под ним без своего лида, плюс явный запрет ссылаться на номера фаз/шагов/блоков где-либо в теле документа.
- **Блок «Следующий шаг» — только фиксированный текст.** DeepSeek приклеивал к шаблонному тексту собственную содержательную оговорку одним абзацем без разделения. Во всех промптах с этим блоком явно написано «ничего от себя — оговорки в разделы выше».
- **Не называть в документах внутренние имена агентов/инструментов** (`account-packager`, `generate_image`) — клиент их не знает. Ссылаться на название следующего **документа** («идёт в `Упаковку профиля`») или на результат простым языком.
- **DeepSeek воспроизводит инструкцию дословно там, где Claude додумывает.** Один и тот же двусмысленный кусок промпта у Sonnet работал годами, а на DeepSeek дал дубль заголовка. Тестировать промпт на той модели, на которой он реально поедет.
- **Модель может застрять в интерактивном режиме.** `expertise.md` не содержал форс-автономного режима (в отличие от `target-audience.md`) — модель выбирала интерактивный диалог и сохраняла как финальный документ «Вопрос 1 (Блок 1)…». Код это не ловил: `parseFrontmatter` тихо возвращал `null`, подставлялся дефолтный статус. Любой промпт, у которого в тексте есть ветки «спросить эксперта», обязан содержать явное «для этого продукта режим всегда автономный».
- **Числовой порог статуса — это пол, а не потолок.** В `visual-style-analyzer` код ставил `статус: боевой` по правилу «3+ референса», не читая, что модель написала о согласованности — а она прямо в теле документа просила не считать профиль боевым. Правило: счётчик может принудительно **занизить** статус при нехватке данных, но не завышать поверх честной самооценки модели.
- **Не добавлять точечные защитные формулировки в промпты генерации изображений реактивно.** Явный запрет на «обрубленные фигуры» привёл к тому, что модель выбрала кадр с человеком, обрезанным по рту — новый, не лучший результат. Правку отменили целиком. Чем больше ограничений, тем сильнее смещаются акценты модели; риск перевешивает пользу от исправления одного случая.
- **Модель обобщает именованные сущности, если не запретить.** `reels-video-generator` превратил «Тандзиро из „Клинка, рассекающего демонов“» в «anime figure with a sword» — видео-модель имени вообще не видела. Промпт теперь требует сохранять узнаваемые визуальные детали именованных персонажей/товаров.
- **Модель честно откажется натягивать несвязанные факты.** `account-packager` отказался сверять рекомендации с «Аудитом шапки профиля», когда в аудите оказались чужие тестовые каналы, — это защита, а не баг, но она означает, что «путь совпадения» на тестовых данных не проверяется. Такие ветки проверяются только на реальном клиенте.

## Проектирование под неполные данные

- **Не считать, что у клиента обе площадки.** `content-planner` был написан с жёстким предположением «есть и Telegram, и ВК», хотя форма разрешает 0–2 own-ссылки. Площадки берутся из `social_links` (role=own), **не** из `account_style_profiles.platforms` (там площадка могла выпасть, если парсер не нашёл постов, хотя клиент её указал). `copywriter` дополнительно падает `PlatformNotInPlanError`, если запрошенной площадки нет в плане. Reels существуют только для ВК.

## Живые тесты

- **Одноразовый magic-токен, использованный тестовым скриптом, недоступен пользователю.** Скрипт, получающий сессию через `GET /api/access/:token`, сжигает ту же ссылку, которую потом нельзя отдать живому человеку. Для таких сценариев генерировать пользователю отдельный второй `access_links`-токен на того же `client_id`.
- **Playwright MCP `browser_snapshot` разворачивает `<details>`** — побочный эффект чтения accessibility-дерева, не баг страницы. Проверять `details.open` прямым `browser_evaluate` сразу после навигации.
