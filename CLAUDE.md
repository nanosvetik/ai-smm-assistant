# CLAUDE.md — Нейро-СММ Ассистент

Проектные инструкции для Claude Code в этом репозитории. Полная архитектура и обоснование решений — в `docs/project-specification.md`, читать его при любой архитектурной задаче. Этот файл — конвенции, рабочий процесс и текущее состояние, не дублирует спецификацию.

## Что за проект

Веб-сервис для мелкого бизнеса и частных экспертов: анализирует их соцсети и конкурентов, распаковывает целевую аудиторию и экспертность, генерирует контент-план и демо-контент (посты, картинки, сценарий Reels) без «нейрослопа». Сейчас — учебный/некоммерческий этап, MVP.

Ключевые документы в репозитории:
- `README.md` — публичное описание проекта (для читателей репозитория на GitHub, не для Claude Code — этот файл дублирует часть контекста ниже в человеко-читаемом виде).
- `docs/project-specification.md` — полный пайплайн, агенты, модели, инфраструктура (актуальная версия).
- `docs/project-specification-original.docx` — исходный черновик от заказчика, оставлен как историческая референс-точка, не редактировать.
- `docs/landing-storyboard.md` — сториборд анимации для лендинга.
- `prompts/target-audience.md`, `prompts/expertise.md`, `prompts/account-analyzer.md`, `prompts/competitor-analyzer.md`, `prompts/profile-header-analyzer.md`, `prompts/account-packager.md`, `prompts/content-planner.md`, `prompts/copywriter.md`, `prompts/visual-style-analyzer.md`, `prompts/visual-generator.md`, `prompts/reels-writer.md`, `prompts/editor-in-chief.md` — системные промпты агентов `audience-unpacker`, `expertise-unpacker`, `account-analyzer`, `competitor-analyzer`, `profile-header-analyzer`, `account-packager`, `content-planner`, `copywriter`, `visual-style-analyzer`, `visual-generator`, `reels-writer`, `editor-in-chief` (`visual-style-analyzer` и `profile-header-analyzer` — сверх исходной таблицы агентов, см. раздел 9 спецификации).
- `smm-mcp/README.md` — документация MCP-сервера генерации картинок/видео (модели, формат вызовов).

## Git-workflow (обязательно)

**Коммитить каждый завершённый этап работы сразу после его завершения** — не батчить несколько этапов в один коммит. Репозиторий подключён к GitHub (`nanosvetik/ai-smm-assistant`, публичный, `origin`) — коммитим прямо в `master` и сразу пушим, без PR-флоу (соло-разработка, PR добавил бы шаг ревью самой себя без реального смысла). Если позже подключится ещё один человек — вернуться к этому решению.

Практически: закончили один логический шаг (одна фича, один агент, один эндпоинт, одна правка документа) — сразу `git add` + `git commit` с внятным сообщением + `git push`. Не ждать «дособрать покрупнее».

`.env` в `.gitignore` — никогда не коммитить секреты (`OPENROUTER_API_KEY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_ADMIN_CHAT_ID`, `VK_SERVICE_TOKEN` — см. «Агенты» ниже — и любые будущие ключи).

## Стек

- **Backend:** Node.js + Express, TypeScript.
- **Frontend:** React + Vite, TypeScript.
- **БД:** SQLite (через Drizzle ORM). Причина выбора: self-hosted одиночный сервер (см. раздел 7 спецификации), не нужен отдельный процесс/контейнер БД, MVP-объём данных небольшой. Если проект вырастет за пределы одного сервера/появится нужда в конкурентной записи — тогда пересматривать на Postgres, не раньше.
- **Пакетный менеджер:** npm, монорепо через npm workspaces (`backend`, `frontend`). `smm-mcp` в workspaces намеренно не входит — это отдельный самостоятельный MCP-сервер со своим `npm install`, см. его README.
- **Хранение файлов:** локальный диск + nginx/Caddy как раздача статики (публичные URL для референсов и сгенерированного медиа) — не S3/R2, см. раздел 7 спецификации.
- **Текстовые LLM:** OpenRouter API. Claude Sonnet 5 — только `visual-style-analyzer` и `profile-header-analyzer` (vision-задачи над фото клиента, не текстом; см. ниже) — vision-часть не подлежит пересмотру этим решением. DeepSeek V4 Pro — все остальные текстовые агенты, **включая `audience-unpacker` и `expertise-unpacker`** (решение сессии 2026-09-01, см. раздел 4 спецификации): контролируемый тест на `expertise.md` ранее показал реальные провалы DeepSeek V4 Pro на сложных мета-шагах промпта против Claude Sonnet 5 (раздел 4 спецификации, «Обоснование распределения моделей») — пользователь сознательно переопределила это решение для MVP/демо-этапа («если в демо-режиме мы всё равно не получим глубину анализа [из-за короткой анкеты онбординга, не из-за модели], не вижу смысла тратить деньги на Sonnet»). Решение провизорное: если живые тесты покажут у DeepSeek те же провалы, что и в контролируемом тесте — вернуть эти два агента на Claude Sonnet 5. Слаги на OpenRouter — с префиксом провайдера (`anthropic/claude-sonnet-5`, не голый `claude-sonnet-5`), формат запроса/ответа — OpenAI-совместимый chat completions (`choices[0].message.content`), не нативный Anthropic Messages API. См. `backend/src/lib/openrouter.ts`. Экспериментальную `deepseek/deepseek-v4-flash-vision-exp` для `visual-style-analyzer` сознательно не стали использовать — потребовала бы включить в OpenRouter разрешение на обучение на входных данных ради дешёвой vision-модели, а вход здесь — drag-and-drop референсы клиента (кабинет, «до/после» и т.п.), не публичные посты; см. «Известные грабли».
- **Медиа-генерация:** `smm-mcp` MCP-сервер (`generate_image`/`generate_video`) — реализован и проверен живыми вызовами к OpenRouter, не переписывать заново. Подробности и подтверждённые слаги моделей — `smm-mcp/README.md`.
- **Данные клиента (ЦА, экспертность, граф знаний):** SQLite, по `client_id` — **не** `@modelcontextprotocol/server-memory`. Решение скорректировано после живого теста (2026-08-29): сервер по умолчанию пишет в один общий файл на весь компьютер (нашли в графе чужую сущность из несвязанного проекта), и даже со scoping через `MEMORY_FILE_PATH` это один stdio-процесс с одним файлом без блокировок при параллельной записи — не годится как хранилище для веб-бэкенда с множеством одновременных клиентов. Подробности — раздел 3 и 7 `docs/project-specification.md`.
- **Уведомления оператору:** Telegram-бот (long polling, не webhook — не требует публичного HTTPS-домена). Требует `TELEGRAM_BOT_TOKEN` и `TELEGRAM_ADMIN_CHAT_ID` в `.env`. Если бот — переиспользуемый (был в других проектах), после первого деплоя обязательно проверить `getWebhookInfo`/`allowed_updates` — см. раздел "Известные грабли" ниже, это реально стоило нескольких часов отладки.

## MCP-серверы

Настроены в `.mcp.json` в корне репозитория:
- `smm-visuals` → `./smm-mcp/src/index.js` — генерация картинок/видео.
- `memory` → `@modelcontextprotocol/server-memory` через `npx` — **память самого Claude Code между сессиями разработки**, не хранилище клиентских данных (см. выше). `MEMORY_FILE_PATH` явно указывает на `./data/dev-memory.json` внутри проекта — без этого сервер по умолчанию пишет в общий файл на весь компьютер, вне привязки к проекту (проверено на практике). Папка `data/` должна существовать заранее — сервер не создаёт её сам, падает с `ENOENT`.

## Текущее состояние бэкенда

Реализовано и проверено живыми вызовами (не только юнит-тестами):
- `POST /api/access-requests` — заявка с лендинга (email/telegram/vk), валидация zod.
- Уведомление оператору в Telegram с кнопками «Одобрить»/«Отклонить» на каждую новую заявку.
- Ручное подтверждение: `npm run admin:list` / `admin:approve -- <id>` / `admin:reject -- <id>` (CLI, не HTTP-админка — намеренно, чтобы не открывать лишнюю поверхность в сеть для self-hosted сервера с одним оператором) — либо те же кнопки в Telegram.
- `GET /api/access/:token` — обмен одноразовой ссылки на сессию (httpOnly cookie). Сгорает по факту первого использования, не по IP (см. раздел 2 спецификации).
- `POST/GET /api/onboarding` — свои соцсети, ссылки конкурентов, опросник (под `requireSession`, пересдача формы перезаписывает предыдущие ссылки/ответы). Опросник — 5 полей: `salesModel`, `clientDescription`, `clientPhrases` (опционально), `expertPath`, `mainPrinciple`, `contentTaboos` — `expertPath` добавлен позже остальных (см. «Текущее состояние фронтенда»), в БД колонка без `NOT NULL` (в таблице уже были тестовые строки без неё), обязательность — только на уровне zod-схемы роута и формы.
- `POST /api/onboarding/references/:category` — загрузка drag-and-drop референса (multer, disk storage под `/uploads/<client_id>/<category>/`). Категория — параметр маршрута, не multipart-поле: порядок частей в multipart не гарантирован, к моменту `destination`-колбэка текстовое поле после файла может быть ещё не распаршено.
- `POST/GET /api/agents/audience-unpacker` — запуск `audience-unpacker` (Claude Sonnet 5 через OpenRouter) на данных онбординга клиента; результат парсится (YAML-frontmatter → статус/b2b/ширина ниши/сегменты отдельными колонками) и сохраняется append-only по версиям в `audience_profiles` — повторный запуск не перезаписывает предыдущую версию молча.
- `POST/GET /api/agents/expertise-unpacker` — тот же паттерн для `expertise-unpacker` (Claude Sonnet 5), с последней версией `audience_profiles` клиента как фоновым контекстом («для кого метод», не цель этой задачи — см. `prompts/expertise.md`, Шаг 0.3), плюс `expertPath` из онбординга как отдельная секция «Путь эксперта» в контексте (закрывает блок «Экспертный путь» промпта — см. «Текущее состояние фронтенда» про находку этой дыры). Результат — append-only в `expertise_profiles` (статус/b2b/методология/структура метода отдельными колонками, статусы только `боевой`/`черновик-рамка`, без skeleton-варианта).
- `backend/src/parsers/` — парсер постов соцсетей, обе платформы: `telegram.ts` (публичная `t.me/s/<channel>`, HTML через `cheerio`), `vk.ts` (`wall.get`, `VK_SERVICE_TOKEN`), общий тип `ParsedPost` (с полем `engagement`: просмотры на обеих площадках, лайки/репосты только на VK) и точка входа `fetchPosts(platform, url)`. Проверено живыми вызовами на обеих платформах.
- `POST/GET /api/agents/account-analyzer` — тот же паттерн, что и unpacker-агенты, но модель `deepseek/deepseek-v4-flash` (не Claude — задача рутинная: эмпирическое описание стиля по факту текста, без сложных мета-шагов). Вход — посты по обеим площадкам из `own`-ссылок клиента через `fetchPosts`, а не форма онбординга. Промпт `prompts/account-analyzer.md` написан с нуля (нет черновика от заказчика), статусы только `боевой`/`черновик-скелет` (без промежуточного «публичные источники» варианта — здесь либо хватает реальных постов эксперта, либо нет). Результат — append-only в `account_style_profiles`. Живой тест прошёл на реальном канале+паблике (38 постов, статус `боевой`, содержательный разбор с дословными цитатами).
- `POST/GET /api/agents/competitor-analyzer` — тот же паттерн, модель `deepseek/deepseek-v4-flash`. Вход — топ-5 постов по вовлечённости на каждого `competitor`-конкурента (просмотры для Telegram; просмотры+лайки×20+репосты×50 для VK — простая эвристика, репосты весят больше как самый активный сигнал, см. `backend/src/agents/competitorAnalyzer.ts`). Промпт `prompts/competitor-analyzer.md` написан с нуля, ищет кросс-паттерны (тема/формат, подтверждённые у 2+ конкурентов независимо) для будущей пометки «формат подтверждён в нише» в `content-planner`. Статус `боевой` требует минимум 2 конкурентов с 3+ постами каждый — код перепроверяет это сам, не доверяя только самооценке модели в frontmatter. Результат — append-only в `competitor_analysis_profiles`. Живой тест на двух реальных каналах прошёл: статус `боевой`, найден и обоснован цифрами один кросс-паттерн.
- `POST/GET /api/agents/profile-header-analyzer` — новый агент сверх исходной таблицы, независим от остальных (нужны только own-ссылки с онбординга). Vision-модель **Claude Sonnet 5** смотрит на реальный аватар/обложку/описание профиля клиента (не референсы, не посты) и даёт чисто фактологическое описание — что там есть, без оценок и рекомендаций (это работа `account-packager`). Парсер расширен: `parsers/vk.ts` — `fetchVkProfileHeader` через `groups.getById` (аватар `photo_max`, обложка — среднеразмерный вариант из `cover.images`, описание); `parsers/telegram.ts` — `fetchTelegramProfileHeader` парсит HTML `t.me/s/<channel>` (`.tgme_page_photo_image img`, `.tgme_channel_info_description`, `.tgme_channel_info_header_title`). Изображения передаются в OpenRouter как есть, публичным URL (не `data:` base64, как у `visual-style-analyzer`, — аватар/обложка и так публичны, скачивать на диск незачем). Статус — чисто механический (`боевой`, если хотя бы по одной площадке получилось скачать аватар), не качественная оценка модели. Результат — append-only в новой таблице `profile_header_profiles`.
- `POST/GET /api/agents/account-packager` — синтезирующий агент (`deepseek/deepseek-v4-flash`) поверх *последних версий* `audience_profiles` + `expertise_profiles` + `account_style_profiles` — требует все три (`PrerequisitesMissingError`, если чего-то нет), не анализирует ничего заново. Плюс **опциональный** четвёртый вход — `Аудит шапки профиля` от `profile-header-analyzer`: если есть, Шаг 4 промпта («Рекомендации по шапке и контактам») строится как реальное сравнение факта с тем, что должно быть, а не абстрактные советы; если нет — работает по-старому, с явной оговоркой в тексте, что реальный профиль не анализировался. Отсутствие аудита не в `PrerequisitesMissingError` и не влияет на итоговый статус упаковки (это дополнительный факт для одного раздела, не показатель качества всего документа) — версия сохраняется в `packaging_profiles.profileHeaderProfileVersion`, `null` если не использовался. Промпт `prompts/account-packager.md` написан с нуля: позиционирование, единый tone of voice, готовый текст био (короткая/расширенная версия), персонализированные (не чек-лист) рекомендации по шапке/контактам для «Аудита профиля». Статус — не выбор модели, а самый слабый статус из трёх *обязательных* входов, код сам считает его (`weakestStatus`) и переписывает строку `статус:` в сохранённом YAML-frontmatter документа через `replaceFrontmatterField`, чтобы текст не расходился с колонкой в БД. Версии всех входов зафиксированы в `packaging_profiles` для трассировки.
- `POST/GET /api/agents/content-planner` — тот же паттерн синтеза (`deepseek/deepseek-v4-flash`), но всего два входа: *последние версии* `packaging_profiles` + `competitor_analysis_profiles` (не сырые ЦА/экспертность/стиль заново — они уже сжаты в Упаковку профиля), плюс **реальные own-площадки клиента** — читаются напрямую из `social_links` (не из `account_style_profiles.platforms`: там могли выпасть площадки без найденных постов, хотя клиент их указал и хочет план именно под них). План строится **только под реальные площадки клиента** — если своя ссылка только на Telegram, плана и идей Reels для ВК в документе не будет вообще (Reels в этом продукте существуют только для ВК); если только ВК — план и Reels только под ВК, без Telegram. Промпт `prompts/content-planner.md` явно требует не «на будущее» планировать площадку, которой у клиента нет. Пометка `[формат подтверждён в нише: ...]` — там, где тема реально адаптирует кросс-паттерн конкурентов, не копирование текста. Только темы/заголовки, без полных текстов и без выбора демо-позиций (это решают `copywriter`/`reels-writer` дальше). Промпт `prompts/visual-generator.md` доработан: готовый английский промпт теперь обязательно обёрнут в ` ```text ` блок (тот же принцип, что и JSON-блок `content-planner`) — `backend/src/lib/imagePrompt.ts` (`extractImagePrompt`) извлекает его оттуда для реального вызова, не парсит вольный markdown. Результат — append-only в новой таблице `generated_images` (без колонки `status` — это медиа-артефакт, не документ с оценкой качества), `visualPromptVersion` — трассировка, каким промптом сгенерирована картинка. Файлы — `workspace/06-images/` (тот же каталог, что и у `smm-mcp`), раздаются на деве через `express.static` (`app.use("/media", ...)` в `index.ts` — на проде эту роль возьмёт nginx/Caddy, раздел 7 спецификации), `frontend/vite.config.ts` проксирует `/media` тем же способом, что и `/api`. **Фронтенд-UX дорабатывался итеративно по прямой правке пользователя после первого живого теста.** Первая версия показывала клиенту весь документ `visual-generator` (русское описание + английский промпт) отдельной кнопкой «Запустить», а под картинкой — модель и цену (`Модель: bytedance-seed/seedream-4.5 · $0.0400`). Пользователь: технические детали генерации клиенту не нужны, а два отдельных клика (сначала промпт, потом картинка) — лишняя сложность. Исправлено — `ImageGenerationBlock.tsx` теперь полностью заменяет `RunBlock` для этапа `visual-generator` (`StagePanel.tsx`, `stage.key === "visual-generator"` — единственный этап, где вместо стандартного рендера документа используется свой компонент целиком, не поверх него): одна кнопка «Сгенерировать картинку»/«Сгенерировать заново» молча вызывает `POST /agents/visual-generator` (тот же `onRun`, что обновляет `results` в `DashboardScreen` — галочка «пройдено» не сломана) и сразу `POST /agents/generate-image`, показывает только готовую иллюстрацию — без промпта, без модели, без цены. `visualPromptVersion`/staleness-проверка убраны как ненужные: раз промпт пишется заново при каждом клике, устаревшей картинки под старый промпт просто не бывает. Плюс кнопка «Скачать картинку» (`<a download>` на `publicUrl`, человеческое имя файла `иллюстрация-<platform>.<ext>` вместо технического таймстемпа) — раздел 6 спецификации требует скачивание медиафайлов в панели экспорта, для картинок реализовано здесь. Живой тест на тестовом клиенте (обе площадки): реальные вызовы Seedream, обе картинки содержательные и без стоковых клише (проверено визуально пользователем — «даже сильнее», триптих на ВК визуально передал сам метод эксперта), скачивание подтверждено. **Видео для Reels (`generate_video`) сознательно не сделано в этой же сессии** — `reels-writer` вообще не пишет английский промпт для видео (только хук/раскадровку/озвучку на русском, нужен отдельный агент-шаг), и `generate_video` требует публичный HTTP(S)-URL для референсных кадров (OpenRouter сам их скачивает, `localhost` в деве недоступен извне) — обе проблемы не связаны с картинками и не решены.

Ещё не реализовано: гейт подтверждения перед генерацией видео для Reels (`generate_video` — см. пункт выше про две нерешённые проблемы), экспорт, results-ссылка.

**Решение на «перед деплоем» (не реализовано сейчас намеренно).** Кнопку «Переделать» в `StagePanel.tsx` убрать для пяти этапов — `audience-unpacker`, `expertise-unpacker`, `account-analyzer`, `competitor-analyzer`, `account-packager`. Причина (пользователь): продукт продаёт честную распаковку — клиент не всегда согласится с тем, что скажет нейро-эксперт, но это должно оставаться фактом, а не подбираемым до нужного ответа. Возможность жать «Переделать», пока не понравится, обесценивает саму честность. `content-planner` явно исключён из списка — пользователь: план это «более гибкий документ», стратегию пересматривать нормально. `copywriter`/`visual-generator`/`reels-writer` кнопку сохраняют — там «Переделать» это обычная творческая итерация (другая формулировка/картинка), не отказ признавать факт о клиенте. Сейчас кнопка нужна во всех девяти для тестового режима.

**Открытый вопрос по `run-all`:** полный прогон занимает ~8 минут — обычный HTTP-запрос от браузера/прокси может не дожить до ответа (типичные таймауты 60–120 сек). Для реального фронтенда `run-all`, скорее всего, придётся переделать в фоновую задачу с отдельной ручкой статуса (поллинг) или SSE/WebSocket-прогресс — решать вместе с фронтендом, не раньше. Кнопка «Запустить анализ» сознательно не входит в срез онбординга ниже — именно из-за этого нерешённого вопроса.

## Текущее состояние фронтенда

Реализован и проверен живыми вызовами через настоящий браузер (React+Vite dev-сервер + прокси на бэкенд): экран онбординга и кабинет эксперта.

- **Magic-ссылка теперь ведёт на фронтенд, не на бэкенд напрямую.** Было: `{BASE_URL}/api/access/:token` — тупик для живого пользователя, ручка отдаёт голый JSON, не HTML. Стало: `{BASE_URL}/onboarding/:token` (`backend/src/admin/approval.ts`) — фронтенд сам вызывает `GET /api/access/:token` из браузера (cookie сессии ставится из fetch-ответа как обычно) и либо показывает форму, либо честный экран ошибки (ссылка использована/просрочена/не найдена) в стиле дизайн-системы, а не сырой JSON. `BASE_URL` по умолчанию теперь смотрит на дев-порт фронтенда (`5173`), не бэкенда (`3000`) — в проде это всё равно один и тот же домен через nginx/Caddy (раздел 7 спецификации), меняется только дев-дефолт.
- **`TokenExchangeScreen`** (`/onboarding/:token`) — вызывает обмен ссылки при монтировании, различает `link_already_used`/`link_expired`/`link_not_found` по коду ошибки и показывает разный текст на каждый случай; при успехе редиректит на `/onboarding`.
- **`OnboardingScreen`** (`/onboarding`) — форма по Брифу 2 из design-brief-ателье.md: короткие поля сверху (модель продаж B2C/B2B, свои соцсети 0–2, конкуренты 2–3 обязательных — `LinksField.tsx`, переиспользуется для обоих списков), ниже — **карточка-интервью** (`InterviewCard.tsx`, сигнатурный элемент экрана): 5 открытых вопросов (см. отдельную находку про пятый — «Путь эксперта» — ниже) поданы как диалог с аватаром-меткой «„» (открывающая кавычка — по-русски читается как «здесь идёт речь», не дженерик иконка вопроса), не стена textarea. Дальше drag-and-drop по 5 категориям референсов (`ReferenceDropzone.tsx`) — каждый файл грузится сразу при дропе через `POST /api/onboarding/references/:category`, не откладывается до сабмита формы. Типографика: **Alegreya** (заголовки, editorial-serif) + **Golos Text** (текст/интерфейс, гуманистический sans) — не Fraunces/Figtree, названные в самом брифе как референс: у обеих нет кириллицы (проверено через Google Fonts metadata API перед выбором, см. «Известные грабли»). Обе гарнитуры самохостятся как `.woff2` в `src/assets/fonts/` — не через Google Fonts CDN в рантайме, тот же self-hosted принцип, что и остальная инфраструктура (раздел 7 спецификации).

Пройденные этапы — изумрудная галочка, текущий (первый непройденный по порядку) — сливовая подсветка строки, остальные — серый текст (`Sidebar.tsx`). При отсутствии предпосылок код переводит `missing` из `PrerequisitesMissingError` в русские подписи (`lib/stages.ts`, `describeMissing`), а не показывает голые agent-слаги.
- **Живой баг: `.every()` на пустом массиве.** `isDone()` в `DashboardScreen.tsx` для площадочных этапов проверял `platforms.every(p => ...)` — на пустом `platforms` (клиент без единой своей ссылки, или протухшая сессия от клиента с пустым онбордингом) `[].every(...)` вакуумно возвращает `true`: «Посты»/«Изображения» показывали галочку «пройдено», хотя ничего не запускалось. Обнаружено пользователем на живом тесте (галочки были не там, где ожидалось), причина — не сам код, а протухшая сессия в браузере от более раннего тестового клиента без ссылок. Исправлено: явная проверка `platforms.length === 0 → false` до `.every()`. Если у площадочного этапа список площадок пуст — правило то же, что и всюду в проекте (см. пункт про клиента с одной площадкой ниже): не считать вакуумную истину прохождением.
- **Живой баг: frontmatter показывался клиенту.** Первая версия `stripFrontmatter` на фронтенде проверяла только самое начало документа (`/^---.../`). Исправлено: `frontend/src/lib/markdown.ts` теперь использует ту же устойчивую логику (перебор всех пар строк `---`, первая, что парсится как YAML-объект через `js-yaml`, добавлен как зависимость и на фронтенд), плюс отдельно съедает окружающий ```` ```yaml ```` фенс.

Вопрос 1 (Блок 1)...») — `expertise.md` (Шаг 0.5) в отличие от `target-audience.md` (Шаг 0.4) не содержал строки «для этого продукта режим всегда автономный», модель сама выбирала интерактивный режим и не могла его продолжить (продукт делает один запрос без чата). Живой повторный тест подтвердил: документ теперь дособирается до конца со статусом `черновик-рамка`, без остановки на интервью.

Урок на будущее: крупный декоративный глиф позади текста — рискованная техника без визуальной проверки в браузере; класть в нормальном потоке рядом с текстом безопаснее, чем накладывать позади него.

- **Кнопка «Скачать таблицу (.xlsx)»** — генерирует `.xlsx` прямо в браузере из тех же структурированных данных, без нового бэкенд-эндпоинта (`lib/contentPlanExport.ts`, библиotека `exceljs`). Два листа: «Контент-план» (та же сетка, что в кабинете, с брендовой сливовой заливкой шапки) и «Идеи Reels» (если есть). **Библиотека выбрана не с первой попытки:** изначально ставили `xlsx` (SheetJS) — но актуальная версия на npm registry (`0.18.5`, последняя опубликованная там) несёт две известных high-severity уязвимости (prototype pollution, ReDoS; патченые версии SheetJS публикует только на свой CDN, не в npm) — заменили на активно поддерживаемый `exceljs`, заодно с более удобным API для стилизации ячеек. `exceljs` подключается через `await import("exceljs")` внутри функции скачивания (динамический импорт), а не статическим `import` вверху файла — библиотека тяжёлая (~940KB), незачем грузить её на каждое открытие кабинета, только по клику «Скачать» (см. `vite build`: без этого основной бандл раздувался почти вдвое).
- **Промпт `prompts/content-planner.md` (Шаг 2) переписан: реалистичная частота публикаций вместо обязательных 14 ежедневных постов на площадку** — см. соответствующий пункт в «Текущее состояние бэкенда» (модель, БД, живой тест).

### Известные грабли (чтобы не наступать повторно)

- **Telegram `allowed_updates`:** Telegram применяет ограничение типов апдейтов, заданное *первым в истории* вызовом `getUpdates` для этого бота — даже из прошлого, не связанного проекта. Без явного `allowed_updates: ["message", "callback_query"]` на каждый вызов кнопки могут молча не долетать, без единой ошибки где-либо. См. `backend/src/lib/telegram.ts`.
- **Windows + `taskkill //F` на фоновый Node-процесс:** может оставить `*.stackdump` в рабочей директории и не дать stdout-буферу сброситься на диск (недостающие строки лога — не всегда баг в коде, иногда просто буферизация). При отладке фоновых процессов проверяй состояние через БД/реальный вызов API, а не только через лог.
- **`npm audit` на `drizzle-kit`:** текущая стабильная `0.31.10` тянет уязвимый transitive `esbuild` (moderate, dev-server only, некритично для `generate`/`migrate`). Более новые `1.0.0-rc.*` ломаются об текущий `drizzle-orm` (`ERR_PACKAGE_PATH_NOT_EXPORTED`) — не апгрейдить туда не проверив совместимость.
- **`js-yaml` под ESM:** `import yaml from "js-yaml"` компилируется без ошибок (`tsc` пропускает через `esModuleInterop`), но падает в рантайме — `does not provide an export named 'default'`. Использовать именованный импорт: `import { load } from "js-yaml"`.
- **Пути к файлам на диске, которые попадут в публичный URL:** `path.relative()` на Windows-деве отдаёт бэкслэши; прод — self-hosted Linux с раздачей статики через nginx/Caddy (раздел 7 спецификации), где бэкслэш в пути ломает URL. Нормализовать на forward slashes (`.split(path.sep).join("/")`) перед сохранением в БД — см. `backend/src/routes/onboarding.ts`, загрузка референсов.
- **OpenRouter и экспериментальные/дешёвые модели:** запрос к `deepseek/deepseek-v4-flash-vision-exp` падал `404 No endpoints available matching your guardrail restrictions and data policy` — privacy/data-policy настройки аккаунта (`openrouter.ai/settings/privacy`) по умолчанию не разрешают маршрутизацию на провайдеров, обслуживающих такие модели (обычно требуют более мягкую политику по обучению на входных данных). Решили не включать это разрешение (данные клиентов — не техническая мелочь) и переключили `visual-style-analyzer` на Claude Sonnet 5 вместо этой модели. Если в будущем понадобится другая экспериментальная/бесплатная модель на OpenRouter — сначала проверять именно эту настройку, не считать 404 багом кода.
- **`parseFrontmatter` ловил не тот блок `---`:** модель иногда вставляет markdown-разделитель `---` в тело документа до настоящего YAML-frontmatter (например, перед ```` ```yaml ```` кодфенсом) — первая non-greedy пара `/---\s*\n([\s\S]*?)\n---/` тогда захватывала произвольный кусок текста между двумя не теми разделителями и валила `js-yaml` (`end of the stream or a document separator is expected`), молча роняя весь запуск агента. Обнаружено при первом сквозном прогоне всей цепочки на `account-packager`. Исправлено — `backend/src/lib/frontmatter.ts` перебирает все пары строк `---` по порядку и берёт первую, которая реально парсится как YAML-объект, а не первую попавшуюся.
- **Статус-порог по счётчику может завысить честность модели:** в `visual-style-analyzer` код изначально ставил `статус: боевой` по одному правилу «3+ референса», не читая, что модель реально написала о согласованности стиля. На первом живом тесте модель прямо в теле документа написала «не считайте это боевым профилем», но её же собственный frontmatter (до фикса промпта) утверждал `боевой` — а код это не ловил вообще, просто переписывал ту же уверенную оценку. Исправлено на паттерн из `competitor-analyzer`: числовой порог — это пол (принудительно занижает при нехватке данных), а не потолок (не завышает автоматически до `боевой`, если модель сама честно написала `черновик-скелет`). При добавлении новых агентов с качественной (не только количественной) оценкой статуса — сразу применять этот паттерн, не изобретать чистый count-based override заново.
- **Не считать, что у клиента обе площадки.** `content-planner` изначально был написан с жёстким предположением «у клиента и Telegram, и ВК» (форма онбординга разрешает 0–2 own-ссылки, `.max(2)` без `.min()` — одна площадка вполне легальна). Обнаружилось не тестом, а прямым вопросом пользователя — стоило проверить раньше, до `reels-writer`, который тоже по дизайну привязан только к ВК. Исправлено: платформы для планирования берутся из `social_links` (role=own), не из `account_style_profiles.platforms` (там площадка могла выпасть, если парсер не нашёл постов, хотя клиент её указал); план и Reels строятся только под реальные площадки; `copywriter` дополнительно проверяет запрошенную площадку против `content_plans.platforms` и падает `PlatformNotInPlanError`, если её там нет. При написании `reels-writer` и `editor-in-chief` — сразу закладывать, что ВК у клиента может не быть вообще.
- **`npm create vite@latest` подсовывает несовместимый стек.** На момент этой сессии scaffold ставил Vite 8 на движке rolldown (нативные `.node`-биндинги) + React 19 + TS 6 — упало сразу на `vite --version` с `Cannot find native binding` (`node_modules/rolldown/...`), несовместимо с установленным Node v20.14.0 (пакеты требуют `^20.19`). Чинить обновлением Node не стали — пересобрали `frontend/package.json` руками на пиновках, совместимых с версией в `backend` (Vite 5, React 18, TypeScript ~5.6, `@vitejs/plugin-react` 4). Перед следующим `npm create vite`/аналогичными generator-командами в этом репозитории — сначала проверять, что образовавшийся стек реально стартует (`npx vite --version`), не доверять дефолтам генератора вслепую.
- **Google Fonts: дефолтные `curl`-запросы не содержат кириллицу.** Fraunces и Figtree — гарнитуры, названные в самом дизайн-брифе как референс, — **не имеют кириллицы вообще** (проверено через `fonts.google.com/metadata/fonts`, поле `subsets`, до скачивания файлов). Отдельно: даже для гарнитур, которые кириллицу поддерживают (Alegreya, Golos Text), запрос к `fonts.googleapis.com/css2` без `Accept-Language: ru-RU` в заголовках отдаёт только `latin`/`latin-ext` блоки — кириллический `@font-face`-блок с нужным `unicode-range` появляется в ответе, только если явно передать этот заголовок. Перед выбором гарнитуры для русскоязычного продукта — сначала проверять `subsets` в Google Fonts metadata API, не полагаться на визуальную похожесть названия на референс из брифа.
- **Кириллица через `curl -d` в Git Bash на Windows — не доверять.** Прямой `curl -X POST ... -d '{"text":"кириллица"}'` из Git Bash на Windows молча портит многобайтовые UTF-8 символы в аргументе командной строки ещё до отправки запроса (в БД долетают кракозябры) — это артефакт консольной кодировки шелла, не баг бэкенда/фронтенда. Тот же запрос через настоящий `fetch()` (Node-скрипт или браузер) идёт с кириллицей без потерь. Для живых тестов с русским текстом на Windows — писать тело запроса в `.mjs`-скрипте и гонять через `fetch`, не через `curl -d` с кириллицей прямо в шелл-команде.
- **`react-markdown` не рисует GFM-таблицы без `remark-gfm`.** Из коробки поддерживается только базовый CommonMark — markdown-таблицы из документов агентов (например, «Сводная сегментация» в Профиле ЦА) рендерились одной строкой текста с символами `|`, не таблицей. Нужен плагин `remark-gfm`, передан в `<ReactMarkdown remarkPlugins={[remarkGfm]}>` (`frontend/src/components/StagePanel.tsx`). Любой новый экран, рендерящий markdown агентов с таблицами/списками задач/зачёркиванием — сразу подключать `remark-gfm`, не только базовый пакет.
- **Одноразовый magic-токен, использованный тестовым скриптом, недоступен пользователю.** При подготовке живого теста кабинета скрипт сам должен получить сессию через `GET /api/access/:token`, чтобы вызвать `POST /api/onboarding` от имени клиента — тем самым сжигает ту же одноразовую ссылку, которую затем нельзя отдать живому человеку (она уже `used_at`). Для тестовых сценариев, где скрипт сам устанавливает данные клиента, генерировать для пользователя отдельный, второй `access_links`-токен (kind: onboarding) на того же `client_id` — не переиспользовать тот, что использовал сам скрипт.

## Конвенции кода

- TypeScript строгий режим (`strict: true`) в обоих пакетах.
- Без комментариев, объясняющих очевидное — только там, где неочевидна причина (см. общие инструкции по написанию кода).
- Не вводить абстракции/фреймворки сверх того, что реально нужно для MVP-объёма (см. принцип self-hosted / без лишних расходов, который уже применялся при выборе БД и хранилища).
- Не создавать пустые папки-заготовки под будущий функционал — добавлять структуру вместе с первым реальным кодом, который её использует.

## MVP-объём (важно не расширять по ходу разработки без явного решения)

- Контент-план на 2 недели — только темы/заголовки.
- Полностью генерируются демо-позиции только по реальным площадкам клиента: до 3 (1 пост Telegram, 1 пост ВК, 1 Reels ВК — Reels только если у клиента есть ВК), меньше — если площадка одна (см. раздел 9 спецификации, «Клиент с одной площадкой»; это решение сессии, не в исходном ТЗ).
- Доступ — только через ручное подтверждение заявки с лендинга, одноразовая magic-ссылка (не привязка к IP — см. раздел 2 спецификации, там объяснено почему).

## Открытые вопросы (см. раздел 8 спецификации)

Не решать эти пункты по умолчанию в одну сторону без обсуждения — они явно оставлены открытыми:
- Полный контент-план с медиа на все 14 дней (следующая итерация после демо).
- Повторный тест `prompts/target-audience.md` на DeepSeek vs Claude.
- Масштабирование хранилища видео при росте числа клиентов.
- `POST /api/agents/run-all` как синхронный HTTP-запрос (~8 минут — риск таймаута браузера/прокси) — решать вместе с фронтендом: фоновая задача с поллингом статуса или SSE/WebSocket-прогресс.
- **`visual-style-analyzer` по-прежнему не запускается никогда в реальном дашборде** (в отличие от `profile-header-analyzer` — см. ниже, для него нашли точечное решение). Только внутри `run-all` (одна из 5 параллельных веток `pipeline.ts`), своей кнопки в сайдбаре нет по дизайну. Раз `run-all` к UI не подключён (пункт выше), реальный клиент, загрузивший референсы на онбординге, никогда не получит их анализ через дашборд. Требует отдельного решения — сюда пару с существующей кнопкой не пристроить так же просто, как для профиля: нужны сами референсы, не только own-ссылки.
