# CLAUDE.md — Нейро-СММ Ассистент

Проектные инструкции для Claude Code в этом репозитории. Полная архитектура и обоснование решений — в `Project Specification v2.md`, читать его при любой архитектурной задаче. Этот файл — конвенции и рабочий процесс, не дублирует спецификацию.

## Что за проект

Веб-сервис для мелкого бизнеса и частных экспертов: анализирует их соцсети и конкурентов, распаковывает целевую аудиторию и экспертность, генерирует контент-план и демо-контент (посты, картинки, сценарий Reels) без «нейрослопа». Сейчас — учебный/некоммерческий этап, MVP.

Ключевые документы в репозитории:
- `Project Specification v2.md` — полный пайплайн, агенты, модели, инфраструктура.
- `target _audience.md`, `expertise.md` — системные промпты агентов `audience-unpacker` и `expertise-unpacker`.
- `landing-storyboard.md` — сториборд анимации для лендинга.
- `README.md` — существующий MCP-сервер `smm-mcp` (генерация картинок/видео через OpenRouter).
- `models.md` — какие модели используются для медиа-генерации.

## Git-workflow (обязательно)

**Коммитить каждый завершённый этап работы в локальный git сразу после его завершения** — не батчить несколько этапов в один коммит. Это временное правило, пока нет GitHub-репозитория: работаем полностью локально, `origin` не настроен. Когда подключим GitHub — правило будет скорректировано (появится push, возможно PR-флоу).

Практически: закончили один логический шаг (одна фича, один агент, один эндпоинт, одна правка документа) — сразу `git add` + `git commit` с внятным сообщением. Не ждать «дособрать покрупнее».

`.env` в `.gitignore` — никогда не коммитить секреты (`OPENROUTER_API_KEY` и любые будущие ключи).

## Стек

- **Backend:** Node.js + Express, TypeScript.
- **Frontend:** React + Vite, TypeScript.
- **БД:** SQLite (через Drizzle ORM). Причина выбора: self-hosted одиночный сервер (см. раздел 7 спецификации), не нужен отдельный процесс/контейнер БД, MVP-объём данных небольшой. Если проект вырастет за пределы одного сервера/появится нужда в конкурентной записи — тогда пересматривать на Postgres, не раньше.
- **Пакетный менеджер:** npm, монорепо через npm workspaces (без Turborepo/Nx — лишняя сложность для текущего размера проекта).
- **Хранение файлов:** локальный диск + nginx/Caddy как раздача статики (публичные URL для референсов и сгенерированного медиа) — не S3/R2, см. раздел 7 спецификации.
- **Текстовые LLM:** OpenRouter API. Claude Sonnet 5 — только `audience-unpacker` и `expertise-unpacker`. DeepSeek V4 (Flash/Pro по задаче) — остальные агенты. Не менять это распределение без повторного теста качества (см. раздел 4 спецификации — там зафиксированы конкретные провалы DeepSeek на сложных мета-инструкциях).
- **Медиа-генерация:** `smm-mcp` MCP-сервер (`generate_image`/`generate_video`) — реализован и проверен живыми вызовами к OpenRouter (см. `smm-mcp/src/index.js`), не переписывать заново. Подтверждённые слаги моделей: `bytedance-seed/seedream-4.5` (картинки, основная), `black-forest-labs/flux.2-max` (картинки, фолбэк), `kwaivgi/kling-v3.0-pro` (видео). Не менять на другие слаги без повторной проверки против `/api/v1/images/models` и `/api/v1/videos/models` — прошлые версии названий (просто "Seedream", "FLUX.2 Max" без слага) не резолвились напрямую.
- **Данные клиента (ЦА, экспертность, граф знаний):** SQLite, по `client_id` — **не** `@modelcontextprotocol/server-memory`. Решение скорректировано после живого теста (2026-08-29): сервер по умолчанию пишет в один общий файл на весь компьютер (нашли в графе чужую сущность из несвязанного проекта), и даже со scoping через `MEMORY_FILE_PATH` это один stdio-процесс с одним файлом без блокировок при параллельной записи — не годится как хранилище для веб-бэкенда с множеством одновременных клиентов. Подробности и обоснование — раздел 3 и 7 `Project Specification v2.md`.

## MCP-серверы

Настроены в `.mcp.json` в корне репозитория:
- `smm-visuals` → `./smm-mcp/src/index.js` — генерация картинок/видео.
- `memory` → `@modelcontextprotocol/server-memory` через `npx` — **память самого Claude Code между сессиями разработки**, не хранилище клиентских данных (см. выше). `MEMORY_FILE_PATH` явно указывает на `./data/dev-memory.json` внутри проекта — без этого сервер по умолчанию пишет в общий файл на весь компьютер, вне привязки к проекту (проверено на практике). Папка `data/` должна существовать заранее — сервер не создаёт её сам, падает с `ENOENT`.

`smm-mcp` требует `OPENROUTER_API_KEY` — берёт его из `smm-mcp/.env` (приоритет) или из корневого `.env` (фолбэк), см. логику загрузки в начале `smm-mcp/src/index.js`.

## Конвенции кода

- TypeScript строгий режим (`strict: true`) в обоих пакетах.
- Без комментариев, объясняющих очевидное — только там, где неочевидна причина (см. общие инструкции по написанию кода).
- Не вводить абстракции/фреймворки сверх того, что реально нужно для MVP-объёма (см. принцип self-hosted / без лишних расходов, который уже применялся при выборе БД и хранилища).

## MVP-объём (важно не расширять по ходу разработки без явного решения)

- Контент-план на 2 недели — только темы/заголовки.
- Полностью генерируются только 3 демо-позиции: 1 пост Telegram, 1 пост ВК, 1 Reels ВК.
- Доступ — только через ручное подтверждение заявки с лендинга, одноразовая magic-ссылка (не привязка к IP — см. раздел 2 спецификации, там объяснено почему).
