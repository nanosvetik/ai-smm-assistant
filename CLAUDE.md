# CLAUDE.md — Нейро-СММ Ассистент

Проектные инструкции для Claude Code в этом репозитории. Полная архитектура и обоснование решений — в `docs/project-specification.md`, читать его при любой архитектурной задаче. Этот файл — конвенции, рабочий процесс и текущее состояние, не дублирует спецификацию.

## Что за проект

Веб-сервис для мелкого бизнеса и частных экспертов: анализирует их соцсети и конкурентов, распаковывает целевую аудиторию и экспертность, генерирует контент-план и демо-контент (посты, картинки, сценарий Reels) без «нейрослопа». Сейчас — учебный/некоммерческий этап, MVP.

Ключевые документы в репозитории:
- `README.md` — публичное описание проекта (для читателей репозитория на GitHub, не для Claude Code — этот файл дублирует часть контекста ниже в человеко-читаемом виде).
- `docs/project-specification.md` — полный пайплайн, агенты, модели, инфраструктура (актуальная версия).
- `docs/project-specification-original.docx` — исходный черновик от заказчика, оставлен как историческая референс-точка, не редактировать.
- `docs/landing-storyboard.md` — сториборд анимации для лендинга.
- `prompts/target-audience.md`, `prompts/expertise.md`, `prompts/account-analyzer.md`, `prompts/competitor-analyzer.md`, `prompts/profile-header-analyzer.md`, `prompts/account-packager.md`, `prompts/content-planner.md`, `prompts/copywriter.md`, `prompts/visual-style-analyzer.md`, `prompts/visual-generator.md`, `prompts/reels-writer.md`, `prompts/editor-in-chief.md` — системные промпты агентов `audience-unpacker`, `expertise-unpacker`, `account-analyzer`, `competitor-analyzer`, `profile-header-analyzer`, `account-packager`, `content-planner`, `copywriter`, `visual-style-analyzer`, `visual-generator`, `reels-writer`, `editor-in-chief` (`visual-style-analyzer` и `profile-header-analyzer` — сверх исходной таблицы агентов, см. раздел 9 спецификации).
- `smm-mcp/README.md` — документация MCP-сервера генерации картинок/видео (модели, формат вызовов).

## Git-workflow (обязательно)

**Коммитить каждый завершённый этап работы сразу после его завершения** — не батчить несколько этапов в один коммит. Репозиторий подключён к GitHub (`nanosvetik/ai-smm-assistant`, публичный, `origin`) — коммитим прямо в `master` и сразу пушим, без PR-флоу (соло-разработка, PR добавил бы шаг ревью самой себя без реального смысла). Если позже подключится ещё один человек — вернуться к этому решению.

Практически: закончили один логический шаг (одна фича, один агент, один эндпоинт, одна правка документа) — сразу `git add` + `git commit` с внятным сообщением + `git push`. Не ждать «дособрать покрупнее».

`.env` в `.gitignore` — никогда не коммитить секреты (`OPENROUTER_API_KEY`, `TELEGRAM_BOT_TOKEN`, `TELEGRAM_ADMIN_CHAT_ID`, `VK_SERVICE_TOKEN`, `SMTP_HOST`/`SMTP_PORT`/`SMTP_USER`/`SMTP_PASS`/`SMTP_FROM` — см. «Агенты» ниже — и любые будущие ключи).

## Стек

- **Backend:** Node.js + Express, TypeScript.
- **Frontend:** React + Vite, TypeScript.
- **БД:** SQLite (через Drizzle ORM). Причина выбора: self-hosted одиночный сервер (см. раздел 7 спецификации), не нужен отдельный процесс/контейнер БД, MVP-объём данных небольшой. Если проект вырастет за пределы одного сервера/появится нужда в конкурентной записи — тогда пересматривать на Postgres, не раньше.
- **Пакетный менеджер:** npm, монорепо через npm workspaces (`backend`, `frontend`). `smm-mcp` в workspaces намеренно не входит — это отдельный самостоятельный MCP-сервер со своим `npm install`, см. его README.
- **Хранение файлов:** локальный диск + nginx/Caddy как раздача статики (публичные URL для референсов и сгенерированного медиа) — не S3/R2, см. раздел 7 спецификации.
- **Текстовые LLM:** OpenRouter API. Claude Sonnet 5 — только `visual-style-analyzer` и `profile-header-analyzer` (vision-задачи над фото клиента, не текстом; см. ниже) — vision-часть не подлежит пересмотру этим решением. DeepSeek V4 Pro — все остальные текстовые агенты, **включая `audience-unpacker` и `expertise-unpacker`** (решение сессии 2026-09-01, см. раздел 4 спецификации): контролируемый тест на `expertise.md` ранее показал реальные провалы DeepSeek V4 Pro на сложных мета-шагах промпта против Claude Sonnet 5 (раздел 4 спецификации, «Обоснование распределения моделей») — пользователь сознательно переопределила это решение для MVP/демо-этапа («если в демо-режиме мы всё равно не получим глубину анализа [из-за короткой анкеты онбординга, не из-за модели], не вижу смысла тратить деньги на Sonnet»). Решение провизорное: если живые тесты покажут у DeepSeek те же провалы, что и в контролируемом тесте — вернуть эти два агента на Claude Sonnet 5. **Похоже, это уже произошло (найдено 2026-09-03, не тестом — пользователь вспомнила и попросила открыть кабинет тестового клиента «держим планку» после вчерашнего запуска).** `expertise_profiles` версии 1 этого клиента (`landing-hero-yoga-client`) содержит не документ, а буквально `<tool_calls><tool_call name="web_fetch">{"url": "https://t.me/derzhimplanku", ...}</tool_call></tool_calls>` — DeepSeek V4 Pro галлюцинировал вызов несуществующего инструмента вместо того, чтобы писать текст (бэкенд не передаёт в OpenRouter вообще никаких `tools`, см. `lib/openrouter.ts` — запрос голый `{model, messages}`). Это более серьёзный провал, чем «поверхностный анализ» из контролируемого теста — не просто ниже качеством, а полный отказ выдать документ вообще; `parseFrontmatter` честно не нашёл там ничего, код подставил дефолтный `черновик-рамка`, фронтенд отрендерил обрывок как обычный текст. Решение принято (2026-09-03): вернуть оба агента на Claude Sonnet 5, но не прямо сейчас — перед деплоем (см. «Открытые вопросы» ниже, этот пункт вынесен туда отдельным чек-листом). Слаги на OpenRouter — с префиксом провайдера (`anthropic/claude-sonnet-5`, не голый `claude-sonnet-5`), формат запроса/ответа — OpenAI-совместимый chat completions (`choices[0].message.content`), не нативный Anthropic Messages API. См. `backend/src/lib/openrouter.ts`. Экспериментальную `deepseek/deepseek-v4-flash-vision-exp` для `visual-style-analyzer` сознательно не стали использовать — потребовала бы включить в OpenRouter разрешение на обучение на входных данных ради дешёвой vision-модели, а вход здесь — drag-and-drop референсы клиента (кабинет, «до/после» и т.п.), не публичные посты; см. «Известные грабли».
- **Медиа-генерация:** `smm-mcp` MCP-сервер (`generate_image`/`generate_video`) — реализован и проверен живыми вызовами к OpenRouter, не переписывать заново. Подробности и подтверждённые слаги моделей — `smm-mcp/README.md`.
- **Данные клиента (ЦА, экспертность, граф знаний):** SQLite, по `client_id` — **не** `@modelcontextprotocol/server-memory`. Решение скорректировано после живого теста (2026-08-29): сервер по умолчанию пишет в один общий файл на весь компьютер (нашли в графе чужую сущность из несвязанного проекта), и даже со scoping через `MEMORY_FILE_PATH` это один stdio-процесс с одним файлом без блокировок при параллельной записи — не годится как хранилище для веб-бэкенда с множеством одновременных клиентов. Подробности — раздел 3 и 7 `docs/project-specification.md`.
- **Уведомления оператору:** Telegram-бот (long polling, не webhook — не требует публичного HTTPS-домена). Требует `TELEGRAM_BOT_TOKEN` и `TELEGRAM_ADMIN_CHAT_ID` в `.env`. Если бот — переиспользуемый (был в других проектах), после первого деплоя обязательно проверить `getWebhookInfo`/`allowed_updates` — см. раздел "Известные грабли" ниже, это реально стоило нескольких часов отладки.

## MCP-серверы

Настроены в `.mcp.json` в корне репозитория:
- `smm-visuals` → `./smm-mcp/src/index.js` — генерация картинок/видео.
- `memory` → `@modelcontextprotocol/server-memory` через `npx` — **память самого Claude Code между сессиями разработки**, не хранилище клиентских данных (см. выше). `MEMORY_FILE_PATH` явно указывает на `./data/dev-memory.json` внутри проекта — без этого сервер по умолчанию пишет в общий файл на весь компьютер, вне привязки к проекту (проверено на практике). Папка `data/` должна существовать заранее — сервер не создаёт её сам, падает с `ENOENT`.

## Текущее состояние бэкенда

Реализовано и проверено живыми вызовами (не только юнит-тестами):
- **`POST /api/access-requests` — заявка с лендинга, только email (решение сессии 2026-09-03, пересматривает более раннее решение той же сессии про выбор канала email/telegram/vk).** Контракт `{ email, name? }` (не `{ contactType, contactValue }`) — `z.string().email()` вместо непустой строки, раз тип значения теперь известен заранее. Причина отказа от выбора канала — по прямым словам пользователя: «почта есть у всех, заодно будет потом куда писать с предложениями» — плюс Telegram/ВК всё равно не могли бы писать клиенту первыми (см. ниже), так что реального выбора для доставки не было. `contactType`/`contactValue` в схеме (`db/schema.ts`) оставлены как есть, только сужен TS/zod-enum до `["email"]` — миграция не нужна, SQLite не хранит CHECK на enum (обычный `TEXT`), колонки не переименовывались. **Не путать с own-соцсетями клиента на онбординге** (`social_links`, Telegram/ВК для контент-анализа) — независимая часть продукта, здесь ничего не меняется. Необязательное `name` (лид-данные) — колонка и zod-поле готовы, собирается лендингом (см. «Текущее состояние фронтенда»).
- Уведомление оператору в Telegram с кнопками «Одобрить»/«Отклонить» на каждую новую заявку — включает имя, если оно есть.
- Ручное подтверждение: `npm run admin:list` / `admin:approve -- <id>` / `admin:reject -- <id>` (CLI, не HTTP-админка — намеренно, чтобы не открывать лишнюю поверхность в сеть для self-hosted сервера с одним оператором) — либо те же кнопки в Telegram.
- **Автодоставка ссылки клиенту на email — реализована и это единственный канал (решение и реализация сессии 2026-09-03, см. раздел 2 спецификации).** По нажатию «Одобрить» (и CLI, и кнопка в Telegram — общая точка `approveRequest` в `admin/approval.ts`) при настроенном SMTP письмо с magic-ссылкой уходит клиенту напрямую (`backend/src/lib/email.ts`, `nodemailer`, универсальная SMTP-обёртка — конкретный провайдер сознательно не выбран, любой транзакционный сервис с SMTP-доступом встанет через `.env` без правки кода: `SMTP_HOST`/`SMTP_PORT`/`SMTP_USER`/`SMTP_PASS`/`SMTP_FROM`). `isEmailConfigured()` — если SMTP не задан, `approveRequest` возвращает `delivered: false`, и оператор (в CLI и в тексте Telegram-сообщения) видит ссылку для ручной пересылки — не ломает существующий флоу, просто не покрывает его автоматикой. Ошибка самой отправки (SMTP недоступен и т.п.) перехватывается и не откатывает уже сохранённое одобрение — клиент и ссылка в БД реальны независимо от письма. Раз канал теперь один, вопрос очерёдности Telegram/ВК (deep-link для `chat_id`, VK Callback API) снят с повестки, не просто отложен. Живой тест через реальный `fetch` (не `curl -d` с кириллицей — см. «Известные грабли») подтвердил: старый контракт `{contactType, contactValue}` отклоняется, невалидный email отклоняется, валидный проходит, `name` с кириллицей сохраняется корректно, полный цикл заявка→одобрение→клиент с `contactType: "email"` в БД пройден до конца. Реальная отправка через настоящий SMTP не проверялась — нечем, пока не выбран провайдер.
- **`GET /api/results/:token` — read-only витрина готового демо (посты/картинки/сценарий рилса/видео), реализована сессией 2026-09-03.** Без `requireSession` — токен в URL и есть авторизация, ссылка рассчитана на пересылку людям без сессии клиента (потенциальные лиды, см. CLAUDE.md/«Текущее состояние фронтенда» про `ResultsScreen`). Сознательно не отдаёт аналитические документы (ЦА, экспертность и т.п.) — только финальный контент. Ссылка (`kind: "results"` в `access_links`, не сгорает при использовании, TTL 90 дней) генерируется и доставляется **автоматически**, не оператором: новая `backend/src/agents/resultsDelivery.ts` (`ensureResultsLinkSent`) вызывается fire-and-forget после каждого сохранения поста/сценария рилса (`routes/agents.ts`), идемпотентно проверяет, готов ли уже весь текстовый демо-контент под реальные площадки клиента, и если да — создаёт ссылку и отправляет на email (переиспользует `lib/email.ts` из пункта выше) либо, если SMTP не настроен, уведомляет оператора для ручной пересылки. **Важно про порядок роутеров в `index.ts`:** `resultsRouter` должен быть смонтирован до `onboardingRouter`/`agentsRouter`/`reelsReferencesRouter` — все три вешают `router.use(requireSession)` без пути, который перехватывает вообще любой запрос, дошедший до роутера (включая чужие пути без совпадающего маршрута), и отвечает 401 сам, не вызывая `next()`; будь `resultsRouter` смонтирован после них, `/api/results/:token` никогда бы до него не доходил — ровно так и произошло при первой проверке, исправлено перестановкой порядка `app.use`. Живой тест на клиенте с обеими площадками (посты, картинки, рилс+видео) подтвердил полный бандл и честный `404 link_not_found` на несуществующий токен.
- `GET /api/access/:token` — обмен одноразовой ссылки на сессию (httpOnly cookie). Сгорает по факту первого использования, не по IP (см. раздел 2 спецификации).
- `POST/GET /api/onboarding` — свои соцсети, ссылки конкурентов, опросник (под `requireSession`, пересдача формы перезаписывает предыдущие ссылки/ответы). Опросник — 5 полей: `salesModel`, `clientDescription`, `clientPhrases` (опционально), `expertPath`, `mainPrinciple`, `contentTaboos` — `expertPath` добавлен позже остальных (см. «Текущее состояние фронтенда»), в БД колонка без `NOT NULL` (в таблице уже были тестовые строки без неё), обязательность — только на уровне zod-схемы роута и формы.
- `POST /api/onboarding/references/:category` — загрузка drag-and-drop референса (multer, disk storage под `/uploads/<client_id>/<category>/`). Категория — параметр маршрута, не multipart-поле: порядок частей в multipart не гарантирован, к моменту `destination`-колбэка текстовое поле после файла может быть ещё не распаршено.
- `POST/GET /api/agents/audience-unpacker` — запуск `audience-unpacker` (Claude Sonnet 5 через OpenRouter) на данных онбординга клиента; результат парсится (YAML-frontmatter → статус/b2b/ширина ниши/сегменты отдельными колонками) и сохраняется append-only по версиям в `audience_profiles` — повторный запуск не перезаписывает предыдущую версию молча.
- `POST/GET /api/agents/expertise-unpacker` — тот же паттерн для `expertise-unpacker` (Claude Sonnet 5), с последней версией `audience_profiles` клиента как фоновым контекстом («для кого метод», не цель этой задачи — см. `prompts/expertise.md`, Шаг 0.3), плюс `expertPath` из онбординга как отдельная секция «Путь эксперта» в контексте (закрывает блок «Экспертный путь» промпта — см. «Текущее состояние фронтенда» про находку этой дыры). Результат — append-only в `expertise_profiles` (статус/b2b/методология/структура метода отдельными колонками, статусы только `боевой`/`черновик-рамка`, без skeleton-варианта).

Пользователь: «невозможно предусмотреть каждый косяк при генерации, чем больше ограничений, тем больше путаешь модель, смещая акценты» — отменила правку целиком, обе добавленные части (Шаг 1 и Шаг 2) убраны, промпт вернулся к состоянию до этой сессии. **Урок на будущее:** не добавлять точечные защитные формулировки в промпты генерации изображений реактивно на каждый отдельный артефакт — риск сместить акцент модели и вызвать новый, не обязательно лучший результат, перевешивает пользу от исправления одного конкретного случая.

**`content-planner` и `copywriter` переведены с DeepSeek V4 Flash на DeepSeek V4 Pro (решение сессии 2026-09-02).** По прямому запросу пользователя после прочтения реального вывода — конкретные примеры названы «полным бредом»: «Утром помято как подушка?» (несвязный образ), «Канализация для лица» (натянутая метафора), «за час снял отёк... за 5 минут» (внутреннее противоречие в самом тексте). Оба агента и так синтезируют поверх уже готовых документов (не сложная мета-аналитика с нуля, как у `audience-unpacker`/`expertise-unpacker`), поэтому изначально казались подходящей задачей для Flash — но на практике связность самого генерируемого текста (не структуры документа) оказалась недостаточной. Изменение — только константа `MODEL` в `contentPlanner.ts`/`copywriter.ts`, промпты и остальной код не тронуты. Живого сравнительного теста Pro против Flash на этой паре агентов не проводилось — решение принято сразу по одному явному примеру, не проверялось повторно.

**Вопрос по `run-all` закрыт как неактуальный (решение сессии 2026-09-03) — фронтенд его не вызывает вообще.** Опасение было в том, что 8-минутный прогон не переживёт обычный HTTP-таймаут браузера/прокси, и `run-all` придётся переделывать в фоновую задачу с поллингом/SSE перед тем, как подключать к реальному UI. На практике кабинет вместо одной кнопки «Запустить анализ» получил кнопку «Запустить» на каждом этапе отдельно (`StagePanel.tsx` → `POST /api/agents/<slug>` напрямую, см. «Текущее состояние фронтенда») — продуктового пути к `run-all` просто нет и не планируется. Эндпоинт и `pipeline.ts` оставлены как есть — полезны для сквозных live-тестов всей цепочки при разработке, не для продукта; переделывать в фоновую задачу незачем, пока не появится реальный сценарий использования.

## Текущее состояние фронтенда

Реализован и проверен живыми вызовами через настоящий браузер (React+Vite dev-сервер + прокси на бэкенд): экран онбординга и кабинет эксперта.

- **Magic-ссылка теперь ведёт на фронтенд, не на бэкенд напрямую.** Было: `{BASE_URL}/api/access/:token` — тупик для живого пользователя, ручка отдаёт голый JSON, не HTML. Стало: `{BASE_URL}/onboarding/:token` (`backend/src/admin/approval.ts`) — фронтенд сам вызывает `GET /api/access/:token` из браузера (cookie сессии ставится из fetch-ответа как обычно) и либо показывает форму, либо честный экран ошибки (ссылка использована/просрочена/не найдена) в стиле дизайн-системы, а не сырой JSON. `BASE_URL` по умолчанию теперь смотрит на дев-порт фронтенда (`5173`), не бэкенда (`3000`) — в проде это всё равно один и тот же домен через nginx/Caddy (раздел 7 спецификации), меняется только дев-дефолт.
- **`TokenExchangeScreen`** (`/onboarding/:token`) — вызывает обмен ссылки при монтировании, различает `link_already_used`/`link_expired`/`link_not_found` по коду ошибки и показывает разный текст на каждый случай; при успехе редиректит на `/onboarding`.
- **`OnboardingScreen`** (`/onboarding`) — форма по Брифу 2 из design-brief-ателье.md: короткие поля сверху (модель продаж B2C/B2B, свои соцсети 0–2, конкуренты 2–3 обязательных — `LinksField.tsx`, переиспользуется для обоих списков), ниже — **карточка-интервью** (`InterviewCard.tsx`, сигнатурный элемент экрана): 5 открытых вопросов (см. отдельную находку про пятый — «Путь эксперта» — ниже) поданы как диалог с аватаром-меткой «„» (открывающая кавычка — по-русски читается как «здесь идёт речь», не дженерик иконка вопроса), не стена textarea. Drag-and-drop референсов на этом экране больше нет — убран решением сессии 2026-09-02 (см. «Текущее состояние бэкенда»), референсы теперь грузятся на странице «Рилсы» в кабинете, после сценария. Кнопка «Запустить анализ» намеренно не входит в этот экран (решение сессии, см. открытый вопрос по `run-all` выше) — сабмит только сохраняет анкету и ссылки.
- **Стек:** React 18 + React Router 6 + Vite 5 + TypeScript ~5.6 (та же версия, что и в `backend`) — **не** версии, которые ставит `npm create vite@latest` по умолчанию на момент этой сессии (см. «Известные грабли»). Без state-менеджера и CSS-фреймворка — простые `useState` и обычный CSS на компонент, оправдано объёмом экрана. `gsap`/`@gsap/react` добавлены сессией 2026-09-03 — только для лендинга (`LandingScreen.tsx`, Бриф 1 требует GSAP-анимацию), в кабинете/онбординге/results не используются.
- **Дизайн-токены** (`src/index.css`) — палитра и правила один в один из design-brief-ателье.md (слива `#4A2545` только акцент, изумруд `#1F5C42` только «готово», не конкурируют за одно значение). Типографика: **Alegreya** (заголовки, editorial-serif) + **Golos Text** (текст/интерфейс, гуманистический sans) — не Fraunces/Figtree, названные в самом брифе как референс: у обеих нет кириллицы (проверено через Google Fonts metadata API перед выбором, см. «Известные грабли»). Обе гарнитуры самохостятся как `.woff2` в `src/assets/fonts/` — не через Google Fonts CDN в рантайме, тот же self-hosted принцип, что и остальная инфраструктура (раздел 7 спецификации).
- **Vite dev-прокси** (`vite.config.ts`): `/api` → `http://localhost:3000`. Тот же same-origin паттерн, что будет в проде через nginx/Caddy (раздел 7) — cookie сессии работает в деве без CORS-настройки на бэкенде.
- Живой тест: полный флоу через реальный `fetch` (не curl — см. «Известные грабли» про кодировку) — обмен ссылки → сессия → `GET`/`POST /api/onboarding` с кириллицей → загрузка референса (multipart) → повторное открытие уже использованной ссылки корректно даёт `link_already_used`. Внешний вид формы визуально подтверждён пользователем в браузере.
- **`DashboardScreen`** (`/dashboard`, «Кабинет эксперта») — сайдбар ровно на 9 пунктов из Брифа 2 (`lib/stages.ts`, `STAGES`), не 1-в-1 с 12 агентами раздела 4: `visual-style-analyzer`/`profile-header-analyzer` — вспомогательные входы без своего пункта, `editor-in-chief` невидим (встроен в `copywriter`/`reels-writer` через `reviewedContent.ts`). Пройденные этапы — изумрудная галочка, текущий (первый непройденный по порядку) — сливовая подсветка строки, остальные — серый текст (`Sidebar.tsx`). Раз кнопка «Запустить анализ» (`run-all`) отложена (8-минутный таймаут, см. выше) — на каждом этапе своя кнопка «Запустить»/«Переделать» (`StagePanel.tsx`), дергает конкретную `POST /api/agents/<slug>` напрямую, без run-all. «Посты»/«Изображения» показывают по площадке клиента отдельным блоком (нужен и telegram, и vk, если оба есть); «Рилсы» — пункт исчезает из сайдбара целиком, если у клиента нет ВК. Документ агента рендерится через `react-markdown` + `remark-gfm` (обычный CommonMark без него не рисует GFM-таблицы, см. «Известные грабли»), frontmatter скрыт (`lib/markdown.ts`, `stripFrontmatter`) — не показываем клиенту служебный YAML, только тело документа. Раздел «Как это работает» заменён на **«То, за что обычно платят маркетологу»** — 5 шагов ценности по реальному порядку пайплайна (портрет ЦА → распаковка экспертности → разбор стиля/ниши → упаковка профиля → готовый контент), каждый явно называет, почему это дорого/сложно сделать самому (например, «здесь чаще всего ошибаются даже опытные маркетологи», «обычно это отдельная дорогая сессия с ментором») — это ответ на прямые слова пользователя: позиционирование ЦА — основная ценность продукта, а не только готовый текст. Новый раздел **«Это только начало»** — глимпс полной SaaS-версии (больше площадок, экспертные вертикальные видео из сырого материала для Reels/TikTok и других площадок, сценарии сторис, воронки в контент-плане) — строит амбицию, ни разу не упоминая слово «демо». **Единственное место на странице, где вообще звучит «демо»** — отдельный блок `.landing-demo-note` прямо у формы заявки (тот же визуальный паттерн, что `.onboarding-success-note`: плум-заливка, левая рамка), с честной формулировкой «демо — не витрина, а по-настоящему рабочая система, только упрощённая: короткая анкета вместо полного интервью даёт более общий, но честный разбор аудитории и метода» — важная правка после первой версии: пользователь поймала переоценку («ваш реальный разбор» звучало как обещание полной глубины) и потребовала переформулировать на «упрощённый, но честный». Форма — `{ email, name? }` через `submitAccessRequest` (`lib/api.ts`), тот же контракт, что и бэкенд. Живой контраст-блок «не шаблон, который выдаст любой чат-бот» (общий ИИ-текст vs реальный голос) — не тронут структурно, только пример подправлен пользователем («гневными высыпаниями» → «сильными высыпаниями», нелепое прилагательное). Бренд-имя `BRAND_NAME = "Своими словами"` — рабочий placeholder, не финальное решение (см. «Открытые вопросы»), вынесен в одну константу для лёгкой замены. Живой тест: форма проходит через dev-прокси фронтенда до бэкенда (`POST /api/access-requests` через `localhost:5173`), `tsc`/`vite build` чистые; визуальный вид в браузере пользователь проверяла сама (dev-серверы), без скриншота для Claude на этот раз.

### Известные грабли (чтобы не наступать повторно)

- **Telegram `allowed_updates`:** Telegram применяет ограничение типов апдейтов, заданное *первым в истории* вызовом `getUpdates` для этого бота — даже из прошлого, не связанного проекта. Без явного `allowed_updates: ["message", "callback_query"]` на каждый вызов кнопки могут молча не долетать, без единой ошибки где-либо. См. `backend/src/lib/telegram.ts`.
- **Windows + `taskkill //F` на фоновый Node-процесс:** может оставить `*.stackdump` в рабочей директории и не дать stdout-буферу сброситься на диск (недостающие строки лога — не всегда баг в коде, иногда просто буферизация). При отладке фоновых процессов проверяй состояние через БД/реальный вызов API, а не только через лог.
- **`npm audit` на `drizzle-kit`:** текущая стабильная `0.31.10` тянет уязвимый transitive `esbuild` (moderate, dev-server only, некритично для `generate`/`migrate`). Более новые `1.0.0-rc.*` ломаются об текущий `drizzle-orm` (`ERR_PACKAGE_PATH_NOT_EXPORTED`) — не апгрейдить туда не проверив совместимость.
- **`drizzle-kit generate` требует настоящий TTY при неоднозначном diff (например, одновременное удаление старых колонок и добавление новых в одной таблице — "это переименование или дроп+создание?") — падает `Error: Interactive prompts require a TTY terminal`, даже если пробовать пропихнуть ответ через `printf ... | npx drizzle-kit generate` (проверено: тоже падает, дело не в содержимом stdin, а в `isTTY`).** В агентской среде (не интерактивный терминал) это тупик — обходной путь: смотреть на текущий `meta/<N>_snapshot.json` (JSON, поля `id`/`prevId`/`tables.<table>.columns`), руками писать новый `meta/<N+1>_snapshot.json` (скопировать предыдущий, поправить нужную таблицу, сгенерировать новый `id` через `crypto.randomUUID()`, `prevId` = `id` предыдущего снапшота) и SQL-файл миграции рядом (для SQLite drop+add колонок в NOT NULL без default — не «ALTER TABLE ADD COLUMN» построчно, а `DROP TABLE`+`CREATE TABLE` целиком, между `PRAGMA foreign_keys=OFF/ON`), плюс дописать запись в `meta/_journal.json`. После — `npm run db:migrate` применяет как обычно (миграции применяются по SQL-файлу и таблице `__drizzle_migrations`, снапшот на этом этапе не участвует), а повторный `npm run db:generate` без TTY подтверждает, что ручной снапшот совпал с реальной схемой (`No schema changes, nothing to migrate`) — так и проверять, что не накосячил руками. См. пример — миграция `0019_normal_captain_flint.sql` (`visual_generator_prompts`, решение сессии 2026-09-02 про визуальный стиль ниже).
- **Ручная запись `when` в `meta/_journal.json` (см. пункт выше про TTY) может тихо отключить все последующие автосгенерированные миграции навсегда, без единой ошибки — найдено сессией 2026-09-03 не тестом, а прямой проверкой БД после того, как две подряд `npm run db:migrate` бодро напечатали «Migrations applied», а нужных колонок не появилось.** Причина — сам мигратор drizzle-orm (`sqlite-core/dialect.js`) применяет только те миграции, у которых `folderMillis` (то самое поле `when` в `_journal.json`) больше, чем `created_at` последней уже применённой строки в `__drizzle_migrations`; порядковый индекс (`idx`) в журнале при этом не участвует вообще. У миграции `0019` `when` был вручную выставлен на круглое время в будущем (`15:00:00.000Z` в день записи) — обе следующие миграции (`0020`, `0021`), сгенерированные `drizzle-kit generate` обычным путём часом раньше по реальным часам, получили `when` меньше, чем уже применённая `0019`, и мигратор их молча пропустил. Никакой ошибки, никакого предупреждения — только явная проверка `PRAGMA table_info(<table>)` на самом файле БД (не доверяя тексту "Migrations applied to ...") это и вскрыла. Исправлено — `when` для 0020/0021 подняты выше значения 0019, после чего `db:migrate` действительно применил обе. **Урок на будущее:** при ручной правке `_journal.json` (единственный случай — обход TTY-ограничения выше) `when` обязан быть больше, чем `when` последней реально применённой в этом файле миграции, не просто «текущее время на момент правки» — иначе любая следующая настоящая `drizzle-kit generate` в реальном будущем молча перестанет применяться, пока это не заметят прямой проверкой БД. После любой ручной правки журнала — всегда сверять `SELECT created_at FROM __drizzle_migrations ORDER BY created_at DESC LIMIT 1` до и после.
- **`js-yaml` под ESM:** `import yaml from "js-yaml"` компилируется без ошибок (`tsc` пропускает через `esModuleInterop`), но падает в рантайме — `does not provide an export named 'default'`. Использовать именованный импорт: `import { load } from "js-yaml"`.
- **Пути к файлам на диске, которые попадут в публичный URL:** `path.relative()` на Windows-деве отдаёт бэкслэши; прод — self-hosted Linux с раздачей статики через nginx/Caddy (раздел 7 спецификации), где бэкслэш в пути ломает URL. Нормализовать на forward slashes (`.split(path.sep).join("/")`) перед сохранением в БД — см. `backend/src/routes/onboarding.ts`, загрузка референсов.
- **OpenRouter и экспериментальные/дешёвые модели:** запрос к `deepseek/deepseek-v4-flash-vision-exp` падал `404 No endpoints available matching your guardrail restrictions and data policy` — privacy/data-policy настройки аккаунта (`openrouter.ai/settings/privacy`) по умолчанию не разрешают маршрутизацию на провайдеров, обслуживающих такие модели (обычно требуют более мягкую политику по обучению на входных данных). Решили не включать это разрешение (данные клиентов — не техническая мелочь) и переключили `visual-style-analyzer` на Claude Sonnet 5 вместо этой модели. Если в будущем понадобится другая экспериментальная/бесплатная модель на OpenRouter — сначала проверять именно эту настройку, не считать 404 багом кода.
- **`parseFrontmatter` ловил не тот блок `---`:** модель иногда вставляет markdown-разделитель `---` в тело документа до настоящего YAML-frontmatter (например, перед ```` ```yaml ```` кодфенсом) — первая non-greedy пара `/---\s*\n([\s\S]*?)\n---/` тогда захватывала произвольный кусок текста между двумя не теми разделителями и валила `js-yaml` (`end of the stream or a document separator is expected`), молча роняя весь запуск агента. Обнаружено при первом сквозном прогоне всей цепочки на `account-packager`. Исправлено — `backend/src/lib/frontmatter.ts` перебирает все пары строк `---` по порядку и берёт первую, которая реально парсится как YAML-объект, а не первую попавшуюся.
- **Двоеточие внутри значения ломает весь YAML-frontmatter, не только это поле — обнаружено пользователем на живом скриншоте («Посты» выглядят «уныло»), не тестом.** Поле `тема:` в `copywriter.md`/`reels-writer.md` копирует тему дословно из контент-плана — а темы там часто в формате «Формат: суть» (например «Личная история: момент, когда я сам заметил автопилот»), то есть само значение содержит `:`. Невалидный YAML (`тема: Личная история: момент...` парсер читает как вложенный маппинг) — `js-yaml.load()` кидает исключение на **всём** блоке, не только на этом поле. Оба места, что полагаются на успешный `load()` для валидации найденного `---...---` блока (`backend/src/lib/frontmatter.ts`, `frontend/src/lib/markdown.ts`), тихо решают «это не настоящий frontmatter» и пропускают его — бэкенд не может подставить корректный статус (`replaceFrontmatterField` возвращает документ как есть), а фронtend не срезает frontmatter вообще, весь сырой YAML-блок утекает в интерфейс как обычный текст. Исправлено в обоих файлах: если прямой `load()` падает, пробуем ещё раз, автоматически взяв в кавычки значения, которые сами содержат `:` (`quoteColonValues`/`isParsableFrontmatter`-хелперы, не переписывают сохранённый документ — только для валидации блока при парсинге). Плюс оба промпта (`copywriter.md`, `reels-writer.md`) теперь прямо просят модель квотировать `тема`, если в ней есть двоеточие — подстраховка на будущее, не единственная защита. Подтверждено живым тестом на реальном сломанном документе из БД (не синтетическом) — `parseFrontmatter` и `stripFrontmatter` оба теперь корректно его читают. **Урок на будущее:** любое новое поле frontmatter, которое копирует свободный текст откуда-то ещё (не жёстко заданный enum вроде `статус`/`платформа`), — потенциальный источник этого же класса бага; закладывать `quoteColonValues`-паттерн сразу, не только реагировать постфактум.
- **Статус-порог по счётчику может завысить честность модели:** в `visual-style-analyzer` код изначально ставил `статус: боевой` по одному правилу «3+ референса», не читая, что модель реально написала о согласованности стиля. На первом живом тесте модель прямо в теле документа написала «не считайте это боевым профилем», но её же собственный frontmatter (до фикса промпта) утверждал `боевой` — а код это не ловил вообще, просто переписывал ту же уверенную оценку. Исправлено на паттерн из `competitor-analyzer`: числовой порог — это пол (принудительно занижает при нехватке данных), а не потолок (не завышает автоматически до `боевой`, если модель сама честно написала `черновик-скелет`). При добавлении новых агентов с качественной (не только количественной) оценкой статуса — сразу применять этот паттерн, не изобретать чистый count-based override заново.
- **Не считать, что у клиента обе площадки.** `content-planner` изначально был написан с жёстким предположением «у клиента и Telegram, и ВК» (форма онбординга разрешает 0–2 own-ссылки, `.max(2)` без `.min()` — одна площадка вполне легальна). Обнаружилось не тестом, а прямым вопросом пользователя — стоило проверить раньше, до `reels-writer`, который тоже по дизайну привязан только к ВК. Исправлено: платформы для планирования берутся из `social_links` (role=own), не из `account_style_profiles.platforms` (там площадка могла выпасть, если парсер не нашёл постов, хотя клиент её указал); план и Reels строятся только под реальные площадки; `copywriter` дополнительно проверяет запрошенную площадку против `content_plans.platforms` и падает `PlatformNotInPlanError`, если её там нет. При написании `reels-writer` и `editor-in-chief` — сразу закладывать, что ВК у клиента может не быть вообще.
- **`npm create vite@latest` подсовывает несовместимый стек.** На момент этой сессии scaffold ставил Vite 8 на движке rolldown (нативные `.node`-биндинги) + React 19 + TS 6 — упало сразу на `vite --version` с `Cannot find native binding` (`node_modules/rolldown/...`), несовместимо с установленным Node v20.14.0 (пакеты требуют `^20.19`). Чинить обновлением Node не стали — пересобрали `frontend/package.json` руками на пиновках, совместимых с версией в `backend` (Vite 5, React 18, TypeScript ~5.6, `@vitejs/plugin-react` 4). Перед следующим `npm create vite`/аналогичными generator-командами в этом репозитории — сначала проверять, что образовавшийся стек реально стартует (`npx vite --version`), не доверять дефолтам генератора вслепую.
- **Google Fonts: дефолтные `curl`-запросы не содержат кириллицу.** Fraunces и Figtree — гарнитуры, названные в самом дизайн-брифе как референс, — **не имеют кириллицы вообще** (проверено через `fonts.google.com/metadata/fonts`, поле `subsets`, до скачивания файлов). Отдельно: даже для гарнитур, которые кириллицу поддерживают (Alegreya, Golos Text), запрос к `fonts.googleapis.com/css2` без `Accept-Language: ru-RU` в заголовках отдаёт только `latin`/`latin-ext` блоки — кириллический `@font-face`-блок с нужным `unicode-range` появляется в ответе, только если явно передать этот заголовок. Перед выбором гарнитуры для русскоязычного продукта — сначала проверять `subsets` в Google Fonts metadata API, не полагаться на визуальную похожесть названия на референс из брифа.
- **Кириллица через `curl -d` в Git Bash на Windows — не доверять.** Прямой `curl -X POST ... -d '{"text":"кириллица"}'` из Git Bash на Windows молча портит многобайтовые UTF-8 символы в аргументе командной строки ещё до отправки запроса (в БД долетают кракозябры) — это артефакт консольной кодировки шелла, не баг бэкенда/фронтенда. Тот же запрос через настоящий `fetch()` (Node-скрипт или браузер) идёт с кириллицей без потерь. Для живых тестов с русским текстом на Windows — писать тело запроса в `.mjs`-скрипте и гонять через `fetch`, не через `curl -d` с кириллицей прямо в шелл-команде.
- **`react-markdown` не рисует GFM-таблицы без `remark-gfm`.** Из коробки поддерживается только базовый CommonMark — markdown-таблицы из документов агентов (например, «Сводная сегментация» в Профиле ЦА) рендерились одной строкой текста с символами `|`, не таблицей. Нужен плагин `remark-gfm`, передан в `<ReactMarkdown remarkPlugins={[remarkGfm]}>` (`frontend/src/components/StagePanel.tsx`). Любой новый экран, рендерящий markdown агентов с таблицами/списками задач/зачёркиванием — сразу подключать `remark-gfm`, не только базовый пакет.
- **Одноразовый magic-токен, использованный тестовым скриптом, недоступен пользователю.** При подготовке живого теста кабинета скрипт сам должен получить сессию через `GET /api/access/:token`, чтобы вызвать `POST /api/onboarding` от имени клиента — тем самым сжигает ту же одноразовую ссылку, которую затем нельзя отдать живому человеку (она уже `used_at`). Для тестовых сценариев, где скрипт сам устанавливает данные клиента, генерировать для пользователя отдельный, второй `access_links`-токен (kind: onboarding) на того же `client_id` — не переиспользовать тот, что использовал сам скрипт.

Подключены и проверены живыми вызовами все 12 агентов: `audience-unpacker`, `expertise-unpacker`, `account-analyzer`, `competitor-analyzer`, `account-packager`, `content-planner`, `copywriter`, `visual-style-analyzer`, `visual-generator`, `profile-header-analyzer`, `reels-writer`, `editor-in-chief` (см. «Текущее состояние бэкенда» выше — там же обоснования по модели и статусной логике каждого; для `profile-header-analyzer` фактологический разбор проверен, а «путь совпадения» с рекомендациями `account-packager` — нет, см. заметку в «Известные грабли»). Текстовый пайплайн бэкенда полностью реализован — не реализованы только гейт медиа-генерации, экспорт, results-ссылка и весь фронтенд (см. «Текущее состояние бэкенда» выше).

**Структура кода агента, зафиксированная решением в этой сессии:** промпт (`prompts/*.md`) и код-оркестрация (`backend/src/agents/*.ts`) — раздельно, не колокация в одну папку на агента. Промпты изначально самостоятельные документы (эксперт может подгрузить их и в любую другую нейросеть напрямую, не только в этот продукт), это не только деталь реализации бэкенда.

## Конвенции кода

- TypeScript строгий режим (`strict: true`) в обоих пакетах.
- Без комментариев, объясняющих очевидное — только там, где неочевидна причина (см. общие инструкции по написанию кода).
- Не вводить абстракции/фреймворки сверх того, что реально нужно для MVP-объёма (см. принцип self-hosted / без лишних расходов, который уже применялся при выборе БД и хранилища).
- Не создавать пустые папки-заготовки под будущий функционал — добавлять структуру вместе с первым реальным кодом, который её использует.

## MVP-объём (важно не расширять по ходу разработки без явного решения)

- Контент-план на 2 недели — только темы/заголовки.
- Полностью генерируются демо-позиции только по реальным площадкам клиента: до 3 (1 пост Telegram, 1 пост ВК, 1 Reels ВК — Reels только если у клиента есть ВК), меньше — если площадка одна (см. раздел 9 спецификации, «Клиент с одной площадкой»; это решение сессии, не в исходном ТЗ).
- Доступ — только через ручное подтверждение заявки с лендинга, одноразовая magic-ссылка (не привязка к IP — см. раздел 2 спецификации, там объяснено почему).

## Открытые вопросы (см. раздел 8 спецификации)

Не решать эти пункты по умолчанию в одну сторону без обсуждения — они явно оставлены открытыми:
- **Конкретный SMTP/email-провайдер для прода** — не выбрано (код-агностик к провайдеру, нужны только переменные в `.env`).
- **Название бренда** — «Ателье» в подвале results-страницы было догадкой Claude по имени файла дизайн-брифа, не подтверждённым названием; убрано по просьбе пользователя. Рабочий домен — `genpost-ai.ru` (уже куплен), сама пользователь считает его тоже слишком айтишным для отображаемого бренда — но домен и бренд не обязаны совпадать. Обсуждение не завершено, черновые варианты: «Голос», «Своими словами», «Мастерская», «Слог», «Портрет».

Закрыт: `POST /api/agents/run-all` как синхронный HTTP-запрос — неактуально, фронтенд его не вызывает (см. «Текущее состояние бэкенда»).

Закрыт (решение сессии 2026-09-03): **повторный тест `prompts/target-audience.md` на DeepSeek vs Claude.** Не нужен отдельным синтетическим прогоном — пользователь сама пройдёт всю цепочку живьём (лендинг → заявка → email → весь пайплайн до генерации видео на DeepSeek), как только будут готовы лендинг и SMTP; поведение Claude на этой паре агентов и так проверено неоднократно раньше, сравнивать по факту будет не с чем — решение по модели примет по результату этого полного прогона, не по отдельному тесту.

Закрыт (решение сессии 2026-09-03): **панель экспорта.** Сужена по прямому решению пользователя — редактируемое текстовое поле с ручной правкой не делаем вообще (клиент копирует текст и правит его сам, где ему удобно, не в инструменте); из раздела 6 остаются только «Копировать текст» и скачивание, оба реализованы в кабинете для `copywriter`-постов (`PostCard` в `StagePanel.tsx`) — кнопка «Копировать текст» (`navigator.clipboard`) и «Скачать текст (.txt)» (тот же паттерн Blob+`<a download>`, что уже используется для контент-плана/картинок/видео). Обе читают текст через `ref.innerText` на отрендеренном `ReactMarkdown`, не сырой `documentMarkdown` — в буфер/файл уходит то, что клиент видит (без `**` и прочего markdown-синтаксиса). Только для постов (`copywriter`) — сценарий рилса не затронут, пользователь просила именно посты. results-страница не тронута — кнопки только в кабинете.

Закрыт (решение сессии 2026-09-03): **полный контент-план с медиа на все 14 дней.** Не следующая итерация — вне рамок проекта вообще: делаем демо, дальнейших итераций после него не планируется.

Закрыт (решение сессии 2026-09-03): **масштабирование хранилища видео при росте числа клиентов.** Значимый прирост числа клиентов/объёма генерации в рамках этого проекта не ожидается.

Закрыт (решение сессии 2026-09-03): **сбор Telegram/ВК клиента после демо для ремаркетинга.** Покрыто уже собираемыми email+именем (см. «Текущее состояние бэкенда») — отдельно собирать tg/vk не будем.

Закрыт (решение сессии 2026-09-03): **решение по референсам для картинок-постов.** Было отложено, но фактически уже закрыто ещё сессией 2026-09-02 — визуальный стиль для картинок синтезирует `account-packager` из текста (позиционирование/ЦА/метод), не `visual-style-analyzer` из фото клиента (см. «Текущее состояние бэкенда»).
